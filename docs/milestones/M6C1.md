## Purpose

M6C1 is only the deterministic geometry layer needed by a later local geofence service. It answers one narrow question: for a validated simple polygon and an E7 coordinate point inside the supported local planar domain, is the point inside, exactly on the polygon boundary, or outside?

This slice deliberately does **not** consume `GnssFix` directly and does not introduce a generic Location abstraction. Future M6C integration must hand it an already accepted fresh position through the correct location/tracking ownership boundary rather than let geometry own GNSS freshness or source arbitration.

## Geometry contract

M6C1 supports:

- simple polygons with 3..64 effective vertices;
- clockwise or counter-clockwise winding;
- concave polygons;
- implicit closing edge or an explicit final vertex equal to the first;
- explicit boundary result;
- deterministic integer-only containment using a winding-number test;
- no dynamic allocation.

Validation fails closed for:

- null/too-short/too-long polygon input;
- coordinates outside the supported local planar coordinate domain;
- adjacent duplicate vertices;
- zero-area/degenerate polygons;
- self-intersecting polygons;
- polygons whose latitude or longitude span exceeds the bounded geometry domain.

Invalid query coordinates are distinguished from a valid point that is merely outside the polygon.

## Arithmetic safety and current span bound

Global E7 coordinates can make naïve cross-product arithmetic overflow signed 64-bit. M6C1 validates a field-scale polygon span before orientation/area operations and translates area calculations around the first vertex.

Current arithmetic bound:

```text
maximum latitude span  = 100,000,000 E7 units = 10 degrees
maximum longitude span = 100,000,000 E7 units = 10 degrees
maximum effective vertices = 64
```

Within that validated domain, current cross products and translated shoelace accumulation remain inside signed 64-bit bounds.

## Independent Astra finding M6C-01 — global coordinate singularities were accepted

Severity: **P2 / geometry-domain correctness**.

The initial code used the ordinary legal latitude/longitude ranges as its planar geometry domain. That admitted exact pole/seam coordinates:

```text
latitude  = -90 or +90
longitude = -180 or +180
```

At those singularities, equivalent physical points can have multiple longitude representations, so a simple planar classifier can return different results for the same physical location.

M6C intentionally remains a local field-scale geometry primitive. The minimal fix is therefore to reject those singularities rather than add spherical/antimeridian logic:

```text
-90 < latitude < +90
-180 < longitude < +180
```

Coordinates immediately inside these limits remain supported subject to the existing polygon/span rules. Exact singular query points return `kInvalidPoint`, not `kOutside`.

Antimeridian-spanning/global polygons remain a separate future geometry requirement and must not be approximated silently.

## Earlier review correction — deterministic oversized fixture

The first owner host run stopped in the malformed-polygon test because the `kMaximumPolygonVertices + 1` fixture was uninitialized. Explicit closing polygons are intentionally supported, so indeterminate first/last values could accidentally appear closed. The fixture was corrected to deterministic data; production semantics remained **64 effective vertices**.

## Deliberate non-goals

M6C1 does not implement or claim:

- `INSIDE / NEAR_FENCE / OUTSIDE` operational state;
- distance-to-fence in meters;
- GNSS quality/freshness checks;
- repeated-fix confirmation or hysteresis;
- FREE_GRAZE;
- LOST/contact logic;
- geofence persistence/configuration storage;
- RF events or ACKs;
- `main.cpp` runtime integration.

`GeofencePointRelation::kBoundary` is geometry truth only. A later reviewed service layer will decide how boundary and near-fence distance map into operational state.

## Ownership and compatibility

```text
geofence_geometry.* -> polygon validity + point relation only
location/tracking    -> accepted fresh position (future integration owner)
geofence service     -> near/outside policy and hysteresis (later)
network/radio        -> unchanged
persistence          -> unchanged
```

Compatibility impact:

```text
Protocol/TLP v1: unchanged
RF/airtime:       unchanged
Storage/flash:    unchanged
GNSS:             unchanged
RAK1904/activity: unchanged
main.cpp runtime: unchanged
RequestedConfig:  unchanged

```

The post-Astra correction only narrows the host-only geometry acceptance domain at exact global singularities.
