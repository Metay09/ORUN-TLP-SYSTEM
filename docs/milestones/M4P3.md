## 1. Product problem

History local `identity` can restart after a destructive partition reset.
Backend dedupe therefore cannot safely identify one observation by
`(DeviceIdentity, identity)` alone.

M4P3 makes the logical observation stream:

```text
(DeviceIdentity, HistoryIncarnation, HistoryRecordIdentity)
```

The incarnation belongs to History observation identity. It is not a role,
gateway identity, credential epoch, user identity or transport property.

## 2. Journal v4 layout

The existing 64-byte static page header is reused without changing capacity:

```text
offset  size  field
0       4     magic ORJ4
4       1     version = 4
5       3     reserved = 0
8       8     page_generation
16      8     device_id
24      8     history_incarnation (nonzero)
32      24    reserved = 0
56      4     CRC32 over bytes 0..55
60      4     commit = 0
```

Unchanged:

- static header size: 64 B
- sequence slot: 16 B
- state slot: 32 B
- page header: 352 B
- record: 36 B
- records/page: 104
- pages: 7
- total History capacity: 728 records
- record encoding and TLP v1 POSITION bytes.

## 3. Incarnation lifecycle

A blank/re-baselined partition requires a fresh nonzero 64-bit incarnation.

Production uses `NrfHistoryIncarnationSource`, a narrow History-owned source
backed by the nRF52840 hardware RNG while SoftDevice is disabled.

Rules:

- blank partition + entropy success -> generate once, then create first v4 page;
- blank partition + entropy failure -> fail closed, no flash mutation;
- normal reboot -> recover incarnation, do not regenerate;
- page rotation -> copy the same incarnation into the new page header;
- all valid pages in one stream must agree on incarnation;
- conflicting valid v4 incarnations -> fail closed;
- destructive full History reset -> next blank boot generates a new
  incarnation before the first new record can become authoritative.

## 4. v3 development cutover

No automatic v3 -> v4 migration is implemented.

A retained v2/v3 History header causes `begin()` to fail closed with
`formatResetRequired() == true`; bytes are not erased or rewritten.

Mixed v3/v4 evidence is also rejected. This avoids assigning a newly invented
incarnation to old observations whose original stream never had one.

A separate controlled development reset/physical qualification step is required
before existing lab hardware with v3 History can run the v4 stream.

## 5. Power-cut / recovery invariant

The incarnation becomes authoritative only through the same sealed static page
header body+CRC / commit-last mechanism already used by History.

If power is lost before a first v4 header is committed, there is no
authoritative new stream yet. On the next blank/torn-only recovery a fresh
incarnation may be generated.

Once any valid v4 page exists, reboot recovers that incarnation and never asks
for fresh entropy.

## 6. Security / privacy

The incarnation is not a secret and is not an authentication key.

It prevents logical observation aliasing across destructive History lifetimes.
Receipt authenticity remains the backend-authority A2D responsibility defined
by M4P1.

Ownership/tenant transfer still requires reviewed same-owner continuity or an
explicit History purge/rebaseline. Reusing retained History under a new owner is
not authorized merely because v4 has an incarnation.

### Required qualification rule — downgrade after v4

Once a device has created committed **v4 History**, do **not** flash a
pre-v4/v3 History firmware onto that device while the v4 History partition is
retained.

Reason: the old firmware does not recognize v4 as retained History evidence.
It can treat the partition as having no valid page and create a v3 page zero,
silently erasing part of the v4 stream.

Therefore:

- v4 -> pre-v4 firmware downgrade with retained History is **forbidden**;
- if downgrade is required, first erase the complete History region
  `0xED000..0xF3FFF`;
- verify the full region reads back erased before booting pre-v4 firmware;
- this is a deliberate destructive development re-baseline, not migration.

For M4P3 physical qualification, the safe path is:

1. read-only classify the current History region;
2. explicitly confirm that current development History may be discarded;
3. erase the entire History region with qualification-only tooling;
4. read back the region and prove it is erased;
5. boot the v4 production image and establish a fresh incarnation;
6. reboot and prove the same incarnation is recovered;
7. prove a normal record-driven page rotation preserves that incarnation.

Do not use a v3 firmware rollback as part of the v4 qualification.
