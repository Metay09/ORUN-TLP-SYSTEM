# M6D3 — Production geofence resource foundation

Status: **ARCHITECTURE CLOSED / IMPLEMENTATION-READY: FOCUSED AUDIT PASS WITH FIXES, ALL REQUIRED DOC CORRECTIONS APPLIED; FOCUSED VERIFY PASS WITH MINOR DOC FIX; 0 BLOCKER / 0 HIGH / 0 MEDIUM; IMPLEMENTATION NOT STARTED**.

Planning branch: `design/m6d3-geofence-resource-foundation`.

## 1. Purpose

M6D2 proves the local geofence behavior but deliberately ships with no
production area set. M6D3 establishes the smallest correct trunk needed to make
that behavior eventually user-configurable without turning BLE, LoRa, ConfigStore
or the map UI into the owner of geofence truth.

The product outcome is simple:

```text
an authorized geofence survives reboot
-> the tracker evaluates exactly that committed area set
-> REPLACE/CLEAR is atomic and stale-write safe
-> a power cut cannot publish half a fence
-> transport loss cannot be mistaken for application success
```

M6D3 does **not** add remote commands, secure EVENT transport, backend alarms,
map UI, FREE_GRAZE, LOST or a new TLP v1 packet.

## 2. Canonical facts carried forward

The current validated/runtime geometry already gives a conservative production
capacity that needs no larger RAM owner:

```text
maximum areas                    = 8
maximum total effective vertices = 64
maximum effective vertices/polygon = 64
GeoPointE7                       = 8 bytes
maximum raw coordinate bytes     = 64 * 8 = 512 bytes
```

These limits come from the existing M6C3 `GeofenceRuntime` budget, not from an
arbitrary UI decision. An optional explicit closing vertex equal to the first
does not consume another effective-vertex slot.

The first production resource therefore freezes **8 areas / 64 total effective
vertices**. Raising that bound later requires its own RAM/CPU/storage/airtime
review; it is not silently widened in this slice.

## 3. Resource semantics

The durable device resource is one complete **permitted-area set**.

It owns together:

- one semantic **configured state**; do not introduce a second independent
  enabled flag;
- zero or more durable polygons according to the semantic rules below;
- its own mutation state token.

The authoritative recovered resource state is three-valued:

```text
CLEAR:
  authoritative, configured = false, zero polygons

CONFIGURED:
  authoritative, configured = true, one or more valid polygons

UNAVAILABLE:
  no authoritative supported resource can be established safely
  (maintenance/re-baseline required)
```

`UNAVAILABLE` is **not CLEAR**. It must be diagnosable, must never be reported
as an intentionally cleared geofence, must never satisfy CLEAR as
`ALREADY_SATISFIED`, and protected mutation must remain blocked until the
later recovery/re-baseline contract establishes fresh authority.

Valid semantic states:

```text
CLEAR_SET:
  configured = false
  area_count = 0
  total_vertices = 0

REPLACE_SET:
  configured = true
  1..8 areas
  3..64 effective vertices per polygon
  total effective vertices <= 64
  complete set passes all existing M6C validation
```

`configured=true + area_count=0` is invalid.

The initial mutation API is whole-resource only:

```text
REPLACE_SET(complete desired snapshot)
CLEAR_SET
```

No durable ADD_VERTEX / DELETE_VERTEX / ADD_POLYGON patch commands are added.
The app may edit incrementally, but the tracker receives one complete candidate.

CLEAR is not FREE_GRAZE and must never be inferred from invalid geometry,
`0,0`, erased bytes, timeout, missing fragments, corruption or unsupported
schema evidence.

Canonical storage uses **effective vertices only**. If an input polygon includes
the optional final closing vertex equal to the first, that duplicate is removed
before canonical comparison/encoding. The durable maximum therefore remains
exactly 64 stored vertices / 512 coordinate bytes.

Canonical equality is byte/field-order identity of the canonical resource
snapshot. M6D3 does not sort polygons, rotate vertex order, reverse winding or
attempt expensive geometric-equivalence detection merely to return
`ALREADY_SATISFIED`. A semantically equivalent shape supplied in a different
canonical sequence may commit as a new revision; permitted-union product
semantics remain unchanged.

## 4. CAS/state-token decision

The geofence resource gets a **separate opaque 96-bit state token** with the
same logical uniqueness model already reviewed for ConfigStore:

```text
geofence_state_token =
    geofence_incarnation[64] || geofence_revision[32]
```

This token is a different namespace from ConfigStore's token.

Reason:

- ConfigStore owns a small independent semantic resource;
- geofence geometry is a separate large resource/persistence owner;
- silently reusing the ConfigStore token would falsely claim atomicity across
  two independent stores;
- a composite multi-store transaction is not required by the current product
  slice and would add unnecessary failure/recovery coupling.

Required semantics:

- incarnation non-zero and established from the platform CSPRNG when a new
  geofence token namespace is created;
- revision starts at 1 and advances exactly once per committed semantic change;
- physical page generation is a separate monotonic `uint64` persistence
  ordering field and is **not** the semantic revision; recovery/maintenance
  writes must not create fake semantic revision transitions;
- two simultaneously committed supported pages with different non-zero
  incarnations are contradictory authority and must fail closed to
  `UNAVAILABLE/UNCERTAIN`, never select one by generation alone;
- A -> B -> A never reuses the first A token;
- identical desired state may resolve as ALREADY_SATISFIED without a flash
  rewrite/token advance once the later mutation service exists, **but only while
  the geofence token is VALID**; UNCERTAIN authority returns
  STATE_UNCERTAIN/UNAVAILABLE rather than ALREADY_SATISFIED;
- CLEAR is a semantic mutation and advances the token when it changes state;
- ambiguous durable outcome is UNCONFIRMED / OUTCOME_UNKNOWN until recovery;
- the token is a precondition identity, not authentication.

## 5. Dedicated flash ownership decision

Existing owned/reserved top-of-application layout:

```text
0x0E7000..0x0E9000  SecurityStore    2 pages
0x0E9000..0x0EB000  ConfigStore      2 pages
0x0EB000..0x0ED000  BLE bond FS      2 pages
0x0ED000..0x0F4000  HistoryStore     7 pages
0x0F4000..           bootloader-owned boundary
```

None of those pages may be reused for geofence.

M6D3 reserves a new dedicated two-page A/B geofence region immediately below
SecurityStore:

```text
0x0E5000..0x0E7000  GeofenceStore    2 pages / 8,192 bytes
```

The application policy ceiling therefore moves from `0x0E7000` to
`0x0E5000`.

With the nRF52840 application link origin at `0x026000`:

```text
new policy application capacity = 0x0E5000 - 0x026000
                                = 782,336 bytes

M6D2 production image           = 250,476 bytes
remaining policy headroom       = 531,860 bytes
```

This reservation does not touch SecurityStore, ConfigStore, bonds, history,
bootloader settings or the bootloader-owned boundary.

It also does **not** claim knowledge of the exact RAK4631 bootloader's
dual-bank/rollback implementation. If a conventional equal-size two-bank model
had to fit entirely below the new policy ceiling, the arithmetic-only image
ceiling would be:

```text
(0x0E5000 - 0x026000) / 2 = 391,168 bytes per bank
```

Against the current 250,476-byte M6D2 production image this leaves about
140,692 bytes of arithmetic margin. This is **not** proof that the actual
RAK4631 bootloader uses that bank model or protects `0x0E5000..0x0F4000`
correctly. The existing bootloader/DFU evidence gate remains open; before BLE
DFU is treated as qualified with GeofenceStore present, the real bootloader must
be shown not to overwrite the geofence/security/config/bond/history reservations.

Two pages are sufficient because the complete first-production geometry is only
512 raw coordinate bytes plus bounded area metadata, header/token/integrity
fields. One full snapshot fits comfortably in one 4 KiB page; the second page
exists for old/new atomicity, not because the payload needs 8 KiB.

The two-page decision assumes **transfer staging is not durable GeofenceStore
authority**. The later BLE/LoRa resource-transfer layer may stage a candidate in
bounded RAM and restart transfer after reboot. If a future product requirement
demands reboot-resumable persistent fragment staging, that storage is a separate
reviewed owner/capacity problem and may require additional pages; it must not
silently consume either committed A/B page.

## 6. Persistence invariant

Geofence persistence is a new sibling owner, not a field added to ConfigStore
and not a blob inside HistoryStore.

The exact on-flash byte layout is frozen by M6D3A, but it must preserve this
invariant family:

```text
recover old committed snapshot
-> erase inactive page
-> write complete new body + integrity data
-> read/verify staged body
-> program activation/commit word last
-> read/verify committed snapshot
-> only then publish new active snapshot/token
```

A reset/power cut before commit must leave the previous committed page
authoritative. No partially written polygon may become visible to
`GeofenceRuntime`.

Unknown/newer format evidence must fail closed; firmware must not guess a future
layout or silently erase it.

Recovery policy must distinguish at least:

- erased/blank first-use evidence;
- valid committed supported CLEAR;
- valid committed supported CONFIGURED;
- supported staged/torn/partial-commit evidence;
- supported committed corruption;
- unsupported/newer schema;
- contradictory committed authority.

If the newest attempted page is torn/corrupt but the older page remains a valid
committed supported snapshot, runtime may continue from that older semantic
snapshot, but the geofence token authority must conservatively become
`UNCERTAIN` until the M6D3B recovery/reconciliation contract proves a single
authoritative outcome. Unsupported/newer schema is never auto-erased.

Reset ownership is also frozen:

```text
ordinary ConfigStore reset -> geofence preserved
BLE unpair                 -> geofence preserved
factory reset              -> explicit geofence re-baseline to authoritative
                              CLEAR under a fresh incarnation
secure decommission        -> later explicit security/product policy; must not
                              be inferred from ordinary config reset
```

## 7. Runtime publication boundary

The durable store owns bytes and authoritative resource state.
`GeofenceRuntime` continues to own only the bounded in-memory copy and point
assessment.

When a valid durable snapshot is published:

### Boot / first publication

- CLEAR/unconfigured -> M6D2 remains unconfigured at base cadence B;
- configured snapshot -> configure the bounded runtime once from that committed
  snapshot.

### REPLACE

The composition owner must, in order:

1. cancel any outstanding additional-fix continuation;
2. abort current geofence confirmation;
3. discard only evidence belonging to the **unfinished** confirmation episode;
   do not drop a representative already selected by a completed episode and
   already handed to / pending in the existing PositionFlow store-before-send
   path;
4. restore/re-anchor to applied base cadence B at the safe scheduling boundary;
5. replace the bounded runtime area set atomically from the newly committed
   snapshot;
6. leave operational state unclassified until fresh accepted Location evidence;
7. emit no synthetic OUTSIDE/INSIDE event solely because config changed.

### CLEAR

The composition owner must:

1. cancel confirmation/continuation;
2. discard only unfinished confirmation evidence; any representative from an
   already-completed episode remains a real accepted POSITION fact and continues
   through PositionFlow;
3. clear the runtime area set;
4. restore base cadence B;
5. emit no synthetic return-to-inside event.

These rules are composition behavior; the store itself must not call GNSS,
PositionFlow or RF.

## 8. Physical flash concurrency

Any production GeofenceStore mutation must join the existing
`FlashMutationGate` single-physical-mutation ownership model once its runtime
store exists.

Do not create a second independent SoftDevice event consumer or a second flash
arbiter.

The exact gate priority is frozen in M6D3B after focused review. The required
ordering constraint is already clear:

- security-critical and live History work must not be starved by a potentially
  larger geofence commit;
- a geofence commit already physically admitted cannot be preempted;
- timeout after SoftDevice acceptance must preserve the existing quarantine /
  late-completion ownership invariant.

## 9. Implementation slices

### M6D3A — layout + format/classifier

**Immediate next code slice.**

Scope:

- add literal `kGeofenceRegionStart = 0x0E5000`,
  `kGeofenceRegionPages = 2` and derived `kGeofenceRegionEnd` to
  `storage_config.h`;
- enforce the exact contiguous chain
  `application | geofence | security | config | bond | history` with
  static assertions, including
  `kGeofenceRegionEnd == kFutureSecurityRegionStart`;
- set
  `kApplicationPolicyEndAddress == kGeofenceRegionStart`;
- fix `check_storage_layout.py::_application_policy_ceiling()` so it derives
  the ceiling from the **lowest reserved-region source of truth** rather than
  continuing to parse `kFutureSecurityRegionStart`;
- make the build script fail closed if the expected geofence/ceiling symbol or
  chain cannot be parsed, update its error text, and add a pure helper
  regression proving the parsed ceiling is exactly `0x0E5000`;
- add a pure portable `geofence_format.{h,cpp}`;
- freeze exact v1 snapshot bytes, including separate physical generation and
  semantic geofence token fields, CRC/commit offsets and forward-schema
  classifier;
- encode/decode authoritative CLEAR and maximum 8-area / 64-effective-vertex
  REPLACE fixtures using canonical effective-vertex-only storage;
- reject malformed counts, overflow, invalid reserved bytes, CRC/commit faults
  and unknown/torn schema evidence;
- expose classifier evidence sufficient for M6D3B to distinguish authoritative
  CLEAR/CONFIGURED from UNAVAILABLE/maintenance and to detect contradictory
  committed incarnations;
- add golden/malformed/power-cut classifier host tests, including:
  - CLEAR golden;
  - maximum 8-area / 64-vertex REPLACE golden;
  - explicit closing-duplicate canonicalization;
  - generation/revision separation;
  - CRC/commit/torn/erased/newer-schema evidence;
  - contradictory-incarnation two-page recovery fixture;
  - build-ceiling parser regression at exactly `0x0E5000`;
- production runtime must still have **no GeofenceStore instance and no writer**.

Non-goals:

- no `FlashMutationGate` change;
- no `NrfGeofenceFlash`;
- no `GeofenceStore`;
- no M6D2 runtime activation;
- no BLE/LoRa/USB mutation;
- no TLP bytes;
- no secure EVENT.

Expected production behavior delta: none. The linked firmware may only observe a
smaller build-time application ceiling; codec code should remain dead-stripped
unless referenced by tests.

### M6D3A acceptance gates from focused architecture audit

M6D3A must not merge unless all of these are true:

1. the linked-image ceiling guard demonstrably enforces `0x0E5000`, not the
   former `0x0E7000`;
2. no application section LMA may enter the reserved geofence range;
3. the codec stores only canonical effective vertices;
4. physical generation and semantic revision are separate fields/contracts;
5. page evidence can distinguish CLEAR / CONFIGURED authority from
   UNAVAILABLE/maintenance evidence;
6. unsupported/newer schema is fail-closed and non-destructive;
7. two committed pages with different incarnations cannot silently select one
   as VALID;
8. production runtime still contains no GeofenceStore writer and no geofence
   configuration activation.

### M6D3B — durable GeofenceStore + flash owner

Only after M6D3A audit/merge:

- implement two-page recovery/commit owner;
- add scoped `NrfGeofenceFlash`;
- add one Geofence client/slot to `FlashMutationGate`;
- establish/recover the independent 96-bit geofence token;
- host fault tests for body/commit/readback/timeout/outcome-unknown;
- before the first destructive writer test on a development unit, take a
  read-only dump/classification of `0x0E5000..0x0E7000`; any non-erased,
  unrecognized content fails closed and is not automatically erased;
- RAK4630 build and focused physical persistence test;
- record wear expectations: an ordinary semantic mutation erases one inactive
  page; using a conservative 10,000 erase-cycle floor gives about 20,000 A/B
  page commits across the pair as engineering arithmetic, not a lifetime
  guarantee. Normal geofence editing must therefore be human/config driven,
  never a high-frequency telemetry loop.

Still no BLE/LoRa mutation and no M6D2 production activation.

### M6D3C — read-only production provider into M6D2

Only after M6D3B:

- boot recovery exposes one immutable active snapshot view;
- wire the committed snapshot into M6D2 using the REPLACE/CLEAR composition
  rules in §7;
- no user mutation transport yet;
- host startup tests for reboot, REPLACE, CLEAR, confirmation cancellation and
  no synthetic event;
- focused GNSS/geofence physical qualification can then validate the real
  durable-source path.

### Later protected transport

BLE and LoRa adapters come only after the store/resource owner exists:

- local application authorization beyond BLE bonding;
- protected LoRa resource transfer under reviewed TLP v2 security;
- fragmentation/reassembly/content digest;
- per-device RESULT/reconciliation;
- group/fleet orchestration and airtime simulation;
- secure OUTSIDE EVENT delivery and backend alarm lifecycle.

## 10. Compatibility invariants

M6D3A/B/C must not change or weaken:

```text
TLP v1 bytes / golden fixtures
RF parameters / relay semantics
HistoryStore format or pages
ConfigStore format/token/pages
SecurityStore format/counters/pages
BLE bond partition
Role / identity / profile ownership
R3 GNSS freshness/session protections
M6D2 3-observation confirmation policy
store-before-send POSITION behavior
```

Geofence token != ConfigStore token.
Geofence persistence != HistoryStore.
BLE/LoRa transport != geofence semantic owner.

## 11. Validation sequence

For every code-bearing M6D3 slice:

```text
focused host tests
-> complete host suite / warnings / sanitizers
-> RAK4630 production build + application-ceiling guard
-> physical persistence/GNSS test only where the slice actually touches it
-> independent Astra audit
-> fixes
-> repeat affected validation
-> merge
```

No build or host result may be reported as physical geofence/power-cut PASS.
