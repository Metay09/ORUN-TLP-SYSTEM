# M2 — Fresh GNSS POSITION packet

> R3 supersedes the historical freshness/UTC and boot-absence details below.
> See [R3 GNSS freshness hardening](../audits/R3_GNSS_FRESHNESS_FIX.md):
> per-callback age, session boundaries, snapshot UTC, bounded detection retry
> and capture-to-live-TX expiry. The wire format and M3 power/schedule policy
> remain unchanged.


## Objective

Extend the universal RAK4630/RAK4631 firmware so a node with a RAK12500
(u-blox ZOE-M8Q) can send a compact binary TLP POSITION packet for a fresh,
valid GNSS fix over the existing private LoRa P2P radio layer. Nodes without
the module remain operational LoRa receivers.

## Implementation summary

- Added a cooperative `GnssManager`. It performs the RAK official example's
  `WB_IO2` power sequence without delays in the main loop, then detects the
  module through I2C. A missing or configuration-failing GNSS reports a short
  log and does not reboot the node or stop radio RX.
- Uses automatic UBX-NAV-PVT and UBX-NAV-DOP callbacks, processed by
  non-blocking `checkUblox()` polling. A candidate POSITION requires matching
  PVT and DOP `iTOW` values, independent of callback order, official u-blox
  fix-validity bits, and coordinate range validation. A separate single-use
  fresh buffer prevents later callbacks from overwriting an unsent fix.
- Adds fixed 34-byte TLP POSITION (`0x02`) serialization/deserialization with
  explicit big-endian encoding and malformed-packet rejection.
- RadioManager owns one sequence counter for both TEST and POSITION packets.
  M1 TEST receive support remains; its periodic test beacon is centrally
  disabled by default to avoid collision with M2 POSITION testing.
- Adds a central 60-second M2 POSITION test interval. The first qualifying
  fresh fix after the interval is transmitted; cached coordinates are not.
- Raises firmware version to `0.2.0-alpha-m2`.

## GNSS library

`sparkfun/SparkFun u-blox GNSS Arduino Library@2.2.29` is used. RAKWireless's
official RAK12500 I2C example uses this library and its `Wire`/UBX approach for
the ZOE-M8Q. It supplies the documented UBX NAV-PVT fix validity, time, PVT
update, NAV-DOP HDOP, and Unix-epoch APIs needed without parsing NMEA.

## GNSS detection method

Following the official RAK12500 I2C example, M2 switches `WB_IO2` low then
high with one-second settling periods, starts `Wire`, and calls the SparkFun
library's I2C `begin` with its documented default u-blox I2C address (`0x42`).
The library uses a bounded 250 ms wait for each I2C detection check and, on
failure, enters an unavailable state while LoRa RX continues.

## Fresh-fix detection method

The automatic UBX-NAV-PVT callback represents an actual newly received
navigation epoch, not a coordinate comparison. It is accepted only with
u-blox `gnssFixOK`, fix type 2D/3D/GNSS+dead-reckoning, valid LLH, and legal
latitude/longitude. UBX-NAV-DOP must have matching `iTOW`; it provides HDOP.
PVT and DOP may arrive in either callback order. A promoted matching epoch is
single-use; a duplicate matching `iTOW` is rejected until another PVT epoch is
observed, without assuming iTOW is monotonic across GPS weeks.

## POSITION packet layout summary

Version `0x01`, type `0x02`, 64-bit hardware device ID, shared 32-bit sequence,
UTC epoch, E7 latitude/longitude, millimetre altitude, HDOP ×100, satellites,
and validity flags form a 34-byte packet. See
[`protocol/M2_POSITION_PACKET.md`](../../protocol/M2_POSITION_PACKET.md).

## Physical hardware validation still required

- Confirm RAK12500 detection in a RAK19007 slot supported by the hardware
  assembly, including its antenna and `WB_IO2` power behavior.
- Confirm outdoor ZOE-M8Q fixes, PVT/DOP `iTOW` pairing, UTC validity, HDOP,
  and the 60-second fresh-fix transmission cadence.
- Confirm a second RAK4630/RAK4631 reports received POSITION packets with the
  expected source, sequence, coordinates, satellite count, RSSI, and SNR.
- Confirm RF range, ERP/antenna compliance, and local regulatory constraints.

## Known issues

- No physical RAK12500, GNSS fix, over-the-air POSITION TX, or peer RX test has
  been performed. Compilation does not validate hardware behavior.
- M2 intentionally omits GNSS power-save/backup behavior, acquisition timeout
  policy, storage, ACK/retry, relay, authentication, and geofencing.

## M3 prerequisites

- Complete and record the physical M2 validation above.
- Define GNSS acquisition timeout, wake/sleep/backup behavior, and configurable
  tracking intervals while preserving the M2 fresh-fix rule and packet format.
