# M6C2 — Host-only permitted geofence area-set semantics

Status: **SOFTWARE VALIDATED; HOST-ONLY; NOT PRODUCTION-INTEGRATED**.

Stacked baseline: `feat/m6c1-geofence-geometry@853622c4849658ec215ae698364c577c1133614b`.
Branch: `feat/m6c2-geofence-area-set`.

## Purpose

M6C2 adds the smallest composition layer required by the product rule that one tracker may have multiple simultaneously permitted polygon areas. It composes already-defined M6C1 polygon geometry as a **union of permitted areas**. It does not add GNSS/location ownership, configuration persistence, near-fence distance, hysteresis or runtime integration.

## Union semantics

For a valid area set and a valid point:

- inside any permitted polygon -> `kInside`;
- otherwise, on the boundary of one or more permitted polygons -> `kBoundary`;
- otherwise -> `kOutside`.

When permitted polygons overlap, `kInside` outranks `kBoundary`. A point that lies on one polygon boundary but is inside another polygon is interior to the permitted union and must not be reported as a boundary-only point.

The returned assessment also carries one matching area index for INSIDE/BOUNDARY diagnostics.

## Fail-closed configuration semantics

The entire area set is validated before point containment is accepted. If any configured polygon is malformed, the result is `kInvalidAreaSet` and the first invalid polygon index is reported. This prevents order-dependent behavior such as accepting a point inside the first valid polygon while silently ignoring a malformed later permitted area.

Null or zero-area inputs are invalid. Invalid query coordinates remain distinct from a valid point that is outside every area.

M6C2 deliberately does **not** freeze an arbitrary product limit on the number of simultaneous permitted areas. The current view consumes a caller-owned finite array and is not connected to runtime or untrusted ingress. Before production integration, the authoritative configuration owner must impose and validate an explicit bounded area-count policy together with its RAM/CPU/storage implications. This avoids inventing a durable product/config limit before the configuration/storage design owns it.

## Ownership and compatibility

```text
geofence_geometry.* -> validity + point-in-one-polygon geometry
geofence_area_set.* -> union semantics across provided permitted polygons
location/tracking    -> accepted fresh position (future integration owner)
geofence service     -> quality, near/outside policy, hysteresis (later)
configuration        -> future bounded area-count/config ownership
network/radio        -> unchanged
persistence          -> unchanged
```

Compatibility impact:

```text
Protocol/TLP v1: unchanged
RF/airtime:       unchanged
Storage/flash:    unchanged
GNSS:             unchanged
RAK1904/activity: unchanged
main.cpp runtime: unchanged
RequestedConfig:  unchanged
Power ownership:  unchanged
```

## Deliberate non-goals

M6C2 does not implement or claim:

- GNSS quality/freshness filtering;
- generic Location or PHONE/MANUAL sources;
- `NEAR_FENCE` distance;
- hysteresis or repeated-fix confirmation;
- FREE_GRAZE;
- LOST/contact semantics;
- persistent polygon configuration;
- RF event/ACK behavior;
- production runtime integration.

The current architecture rule remains: M6 local geofence may proceed, but trustworthy network-contact LOST remains gated on authenticated receipt/contact semantics. `TX_DONE` is not contact.

## Validation

Owner-run full host regression on the final M6C2 code/test tree: **PASS**.

The M6C area-set suite freezes:

- null/empty area-set rejection;
- inside a later permitted polygon -> inside union;
- boundary-only point -> boundary;
- boundary of one polygon + inside another -> inside union;
- the same INSIDE-over-BOUNDARY precedence with polygon order reversed;
- outside all polygons -> outside;
- malformed later polygon invalidates the entire set before containment;
- invalid query coordinate remains distinct from outside;
- M6C1 explicit closing-vertex semantics compose correctly.

The full retained B1A/B2/B3/B4, M3/M4/M5, R2/R3/R4 and M6A/M6B/M6C1 host regressions also passed in the same run. M6C tests use the current `gnu++11`, `-Wall -Wextra -Werror`, ASan/UBSan profile.

Owner-run `pio run -e rak4630`: **SUCCESS** with GCC ARM 7.2.1. The bounded Wire and SX126x driver patch guards were verified/applied. Build size:

```text
RAM:   13,932 / 248,832 bytes = 5.6%
Flash: 141,928 / 815,104 bytes = 17.4%
```

The linked firmware size remains unchanged because `geofence_area_set.cpp` is not referenced by `main.cpp`. No new ORUN project warning was observed; emitted warnings were the existing pinned third-party SX126x warnings.

No firmware upload or physical hardware validation is required for M6C2 itself because this slice is pure deterministic composition and not runtime-integrated. This does not validate real GNSS geofence behavior, field false-alarm performance, `NEAR_FENCE`, hysteresis, persistence or alarms.
