# M7P3 — SoftDevice-compatible asynchronous history flash backend

Status: **HOST PASS; BUILD PASS; NO RUNTIME BEHAVIOR CHANGE ON REAL HARDWARE;
SOFTWARE/BUILD VALIDATED, SOFTDEVICE-ENABLED PHYSICAL FLASH MUTATION NOT YET
PHYSICALLY VALIDATED.**

Baseline: `main@de4d6cd1d782e55eead2215bf4c03e6932049ea4` (M7P2 merged).
Branch: `feat/m7p3-async-history-flash`.

## Purpose

M7P1 (ADR) decided, and M7P2 reserved flash pages for, a future
SoftDevice-enabled runtime. Both are inert until the existing history
persistence path can actually survive SoftDevice being enabled — today it
fails closed the instant SoftDevice is on
(`docs/architecture/ORUN_STORAGE_FLASH_OWNERSHIP.md` §8). M7P3 makes the
*existing* history path capable of asynchronous SoftDevice-enabled flash
mutation, in software, **without enabling BLE or SoftDevice in shipped
runtime**. No BLE advertising, services, pairing, DFU, or bond storage is
added; those remain later slices (see `docs/architecture/ADR_M7_PERSISTENCE_LAYOUT.md`
§16).

## Actual installed framework evidence (not assumed)

Read directly from the installed Adafruit nRF52 1.7.0 core and S140 6.1.1
SoftDevice API headers, per the task's explicit requirement not to rely on
memory for SoftDevice event semantics:

- `sd_flash_write`/`sd_flash_page_erase` (`nrf_soc.h`): with SoftDevice
  enabled, the call only *starts* the command; completion is communicated
  later by exactly one of `NRF_EVT_FLASH_OPERATION_SUCCESS` or
  `NRF_EVT_FLASH_OPERATION_ERROR`. Retvals include `NRF_ERROR_BUSY` ("the
  previous command has not yet completed") alongside permanent-rejection
  codes (`NRF_ERROR_INVALID_ADDR`, `NRF_ERROR_INVALID_LENGTH`,
  `NRF_ERROR_FORBIDDEN`, `NRF_ERROR_INTERNAL`). With SoftDevice disabled, the
  call is fully synchronous and returns `NRF_SUCCESS` only once the
  write/erase has completed — matching `NrfHistoryFlash`'s existing,
  unmodified behavior exactly.
- `sd_evt_get(uint32_t* p_evt_id)` (`nrf_soc.h`): a plain, Bluefruit-independent
  Nordic SVC. "The application should keep calling this function to get
  events, until `NRF_ERROR_NOT_FOUND` is returned." This is what M7P3 calls
  directly; it does not depend on, and is never called concurrently with,
  Bluefruit's own event pump (which is never started — BLE is not enabled).
- The framework's own reference implementation for this exact problem
  (`libraries/InternalFileSytem/src/flash/flash_nrf5x.c`, `fal_erase`/
  `fal_sub_program`) retries any non-success `sd_flash_*` return up to 20
  times with a short delay, and reports completion via a callback
  (`flash_nrf5x_event_cb`) that is **only ever invoked from Bluefruit's own
  SoftDevice event-processing task** (`bluefruit.cpp:711`,
  `if (flash_nrf5x_event_cb) flash_nrf5x_event_cb(soc_evt);`) — i.e., that
  callback never fires unless `Bluefruit.begin()` has been called. Since
  M7P3 must not start BLE, this existing framework path is not usable as-is;
  `FlashMutationGate` instead pumps `sd_evt_get()` itself, directly, from the
  cooperative main loop (§below) — a genuinely different,
  Bluefruit-independent event source, not a reuse of Bluefruit's pump.
- The framework's InternalFS backend also blocks the calling task on a
  FreeRTOS semaphore while waiting for that event
  (`wait_for_async_flash_op_completion`, `xSemaphoreTake(_sem, portMAX_DELAY)`).
  `FlashMutationGate` deliberately does **not** copy this: ORUN's whole
  architecture is a single cooperative loop with no blocking waits anywhere
  else, and the task brief explicitly requires "do not block inside callback
  context" / poll-from-service-context instead.
- `sd_softdevice_is_enabled()` was already called unconditionally on every
  boot by `NrfHistoryFlash` before M7P3 (proven safe on real hardware since
  M4/M6P1's physical closures); `FlashMutationGate` reuses that exact same
  safe pattern, and only calls `sd_evt_get()` when that check reports
  SoftDevice is genuinely enabled — never unconditionally, since `sd_evt_get`
  requires the SoftDevice SVC vector to actually be installed.

## FlashMutationGate

New `firmware/include/flash_mutation_gate.h` / `firmware/src/flash_mutation_gate.cpp`.
Single client today: `HistoryStore`. Does not implement or queue non-existent
future clients (config/security/bond, per the ADR — those remain M7P5/M7P6).

- **SoftDevice-disabled path**: delegates byte-for-byte to an owned
  `NrfHistoryFlash` instance — the exact same, unmodified, already-audited
  synchronous code and guards as before M7P3. This is the only path
  exercised by shipped firmware, since nothing in this slice enables
  SoftDevice.
- **SoftDevice-enabled path** (host-tested only, not yet run on real
  hardware — see "Physical validation" below): issues `sd_flash_write`/
  `sd_flash_page_erase` directly, independent of Bluefruit/InternalFS.
- **Readiness**: `begin()` sets an internal `ready_` flag from
  `NrfHistoryFlash::begin()`'s result; `program()`/`erasePage()` fail closed
  on `!ready_` before doing anything else, on both the sync and async
  branches — an independent guard, not a reliance on `HistoryStore` never
  calling this backend before a successful `begin()`.
- **Operation states**: `Kind::kNone` (idle) → submit → `kPending`
  (`submission_accepted_ == false`, still retrying past `NRF_ERROR_BUSY`) →
  `kPending` (`submission_accepted_ == true`, awaiting the SoftDevice event)
  → `kDone`/`kFailed` (event observed, or bounded timeout). Exactly one
  physical Nordic flash mutation is ever in flight through this gate; a
  second `program()`/`erasePage()` call while one is outstanding is rejected
  (`kFailed`) rather than queued or silently dropped.
- **`NRF_ERROR_BUSY` handling**: never spins or blocks. A busy result is
  reported as `kPending`; the caller retries via `pollPending()` from normal
  loop/poll context on a later pass. Bounded by the same 4-second timeout
  used for awaiting the completion event (not a separate unbounded retry
  budget), so a persistently busy SoftDevice cannot wedge the request
  forever either.
- **Source-buffer lifetime**: `program()` copies the caller's data into an
  owned `staging_[storage_config::kPageHeaderSize]` member before ever
  calling `sd_flash_write`; the caller's original buffer is never touched or
  referenced again after `program()` returns. Verified by a host test that
  corrupts the original buffer immediately after submission and confirms
  the eventually-programmed bytes still match the original data (test C).
- **Event routing (`pumpEvents()`)**: drains `sd_evt_get()` in a loop until
  `NRF_ERROR_NOT_FOUND`, recording only `NRF_EVT_FLASH_OPERATION_SUCCESS`/
  `ERROR` for the current in-flight request; any other SoC event (HFCLK,
  power, radio timeslot, USB) is drained (so the queue never backs up) but
  otherwise ignored — this slice does not add handlers for them. A flash
  event with nothing in flight, or a second flash event before the first is
  consumed, is counted as `spurious_events` and discarded rather than
  completing the wrong request or double-calling completion (test I).
- **Timeout**: 4 seconds from submission. On timeout the request fails
  closed (`kFailed`) and the gate becomes reusable; this is not a claim
  about whether the physical write/erase happened, only that the
  application will not wait on it forever (test: dedicated timeout case).
- **Reentrancy**: `pumpEvents()` only ever writes a completion flag/result
  (`event_ready_`/`event_success_`); it never itself advances
  `HistoryStore`'s state machine or calls into `PositionFlow`/radio code.
  The actual logical-state advancement happens later, from
  `HistoryStore::poll()` in normal loop context, called separately from
  `main.cpp`'s loop() — matching the task's preferred "event callback
  records a minimal signal; loop context advances state" pattern.

## HistoryStore integration

`journal_format` bytes are **unchanged** — no static_assert, struct layout,
CRC, or commit-word semantics were touched. `HistoryStore::writeBlob()` was
restructured into an explicit `BlobStep` (`kBody` → `kCommit` → `kVerify`)
so a `kPending` result from the body or commit-word program() call resumes
on a later `poll()` pass via `pollPending()` instead of resubmitting or
skipping ahead. The body-then-separate-final-commit-word order, and the
requirement that both physical programs land before the record is
considered committed, are exactly as before. `kVerify`'s read is always
synchronous (flash reads are plain memory reads, not a SoftDevice SVC — even
`NrfHistoryFlash::read()` never checked SoftDevice state), so it is never
affected by `kPending`. The erase branch of `poll()` got the equivalent
treatment. On the **SoftDevice-disabled path** (the only path shipped
firmware exercises today), every physical primitive resolves synchronously
on its first call, so this refactor produces **identical observable timing**
to the pre-M7P3 code — proven by the full pre-existing host suite (all 33
prior tests, including the exact `M4 production backend synchronous/
SoftDevice guard checks` scenario) passing unchanged.

## Store-before-send / PositionFlow

**No changes were made to `position_flow.h`/`position_flow.cpp`.**
`PositionFlow` was already structured around polling `HistoryStore::
takeAppendResult()` across however many `update()`/`poll()` ticks an append
takes, rather than assuming synchronous completion — a design already in
place since M4. This means the existing store-before-send state machine
(`appending_` blocks a second `acceptFix()`; `live_pending_`, and therefore
any TX, is only set after `takeAppendResult()` reports success) was already
correct for an async-completing backend. This claim is not asserted without
evidence: `firmware/tests/m7/test_m7p3_history_async.cpp` (test H) drives a
backend that stays `kPending` for several ticks and confirms no TX is
attempted before `kStored` fires, a concurrent fix is rejected while the
first is still pending, and a storage failure suppresses TX entirely for
that record.

## SoftDevice OFF / ON behavior summary

```text
SoftDevice OFF (shipped M7P3 runtime, always, since BLE is not started):
  FlashMutationGate delegates to the unmodified NrfHistoryFlash path.
  Identical behavior/timing to pre-M7P3. Proven by the full pre-existing
  host suite passing unchanged, and by the RAK4630 build/ELF evidence below.

SoftDevice ON (host-tested only in this slice; nothing enables it on
real hardware here):
  FlashMutationGate issues sd_flash_write/sd_flash_page_erase directly,
  tracks kPending, drains completion via sd_evt_get(), and only reports
  kDone/kFailed once the matching event (or a bounded timeout) resolves it.
```

## Timeout/error/reset semantics

- A lost/missing completion event fails the request closed after 4 seconds;
  it never claims the write succeeded or failed at the physical level, only
  that the application stops waiting.
- No RAM-resident pending/queue state is assumed to survive a reset.
  Recovery authority remains flash content only, exactly as before:
  `HistoryStore::recover()` is unchanged, and a physical write that landed
  in flash but whose completion (and therefore its commit word) was never
  observed before a simulated power interruption is recovered as **absent**,
  identically to the pre-M7P3 synchronous torn-write case (test G).

## Limitations

- **HOST PASS != PHYSICAL PASS.** The SoftDevice-enabled asynchronous path
  (busy retry, real event delivery timing, real `sd_evt_get` behavior under
  actual SoftDevice load, real flash program/erase timing while SoftDevice
  is active) has **not** been exercised on real hardware — nothing in this
  slice enables SoftDevice on the device. **Software/build validated;
  SoftDevice-enabled physical flash mutation not yet physically validated.**
- The 4-second timeout is a bounded, reasonable-looking value, not derived
  from a measured worst-case SoftDevice flash-operation latency; it should
  be revisited once real timing data exists (M7P7, when SoftDevice is first
  actually enabled).
- `FlashMutationGate` is the sole owner of `sd_evt_get()` today. If a future
  slice (M7P7) also starts Bluefruit, Bluefruit's own internal event pump
  would compete for the same global SoftDevice event stream — this is a
  real future integration point, not resolved here, and is called out
  explicitly so it is not rediscovered by surprise later.
- No physical bootloader/DFU facts are touched or newly resolved by this
  slice (decision gate F, `ORUN_STORAGE_FLASH_OWNERSHIP.md`, remains
  unresolved).

## Independent/self-review

A local `/code-review high` self-review pass on this diff (**not** the
cloud multi-agent `/ultrareview` — that requires user-triggered billing
this session cannot invoke on its own, and is not claimed here) found
three real issues, all addressed before the commit below:

1. `FlashMutationGate::program()`/`erasePage()` had no readiness gate of
   their own on the async path — fixed by adding an independent `ready_`
   flag, set in `begin()` (see "Readiness" above).
2. A declared-but-unused `kMaxSubmitAttempts` constant, with a misleading
   comment implying a fixed 20-attempt retry bound that the code never
   actually enforced (the real bound is the wall-clock timeout) — removed
   the dead constant and corrected the comment to describe the actual
   timeout-based enforcement.
3. `program()`/`erasePage()` re-check SoftDevice state even when about to
   delegate to `sync_backend_`, which performs the same check again
   internally — reviewed and kept as intentional defense-in-depth (removing
   either check would either weaken `NrfHistoryFlash`'s own independent
   guard or remove the gate's own branch-selection check), with a comment
   added explaining why, rather than "fixed" by deletion.

All fixes were re-validated: host tests 35/35 PASS, `pio run -e rak4630`
SUCCESS, and the FlashMutationGate test binary re-run directly.

## Physical validation status

Not performed in this slice, consistent with the task brief's explicit
preference: implement/test/build/review/merge in software first, and
schedule focused physical SoftDevice flash validation before or as part of
the first M7 slice that actually enables SoftDevice/BLE runtime (M7P7).
Nothing in M7P3 enables SoftDevice or BLE in shipped firmware, so there is
no physical SoftDevice-enabled behavior to validate yet — only the
unchanged SoftDevice-disabled path, which is the one running on real
hardware, and which the existing physical M0–M6P2 closures already cover.
