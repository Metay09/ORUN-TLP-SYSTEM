Branch: `feat/m7p5-durable-config-store` (PR #15, open, not yet merged).

## Purpose

M7P1 decided, and M7P2 reserved, a durable-config partition at
`0x0E9000..0x0EB000` (2 pages). M7P5 implements the real owner:
`ConfigStore`, a raw versioned A/B store persisting exactly two fields —
`tracking_interval_seconds` and `battery_capacity_mah` — and wires
`tracking_interval_seconds` in as the authoritative runtime GNSS schedule
interval. This is deliberately **not** the B4 requested-config migration:
`tracking_enabled`, relay forwarding, role, location source, profile and
capability are untouched, still runtime-only, and still owned by B4's
`RequestedConfig`/`CapabilitySnapshot`/`EffectiveConfig` pipeline.

## Config schema v1

`firmware/include/config_format.h`:

```text
tracking_interval_seconds : uint32   (custom values supported, not an enum)
battery_capacity_mah      : uint32   (0 = unspecified)
```

- Default remains exactly 180 seconds (`gnss_config::kTrackingIntervalSeconds`,
  unchanged). Blank flash, a corrupt page, or a `ConfigStore::begin()` failure
  all leave `config()` reporting this same default — never a zeroed or
  undefined interval.
- Candidate validation reuses `gnss_config`'s existing bound
  (`kMaxTrackingIntervalSeconds = 12 * 24 * 60 * 60`, factored out of the
  pre-existing static_assert so there is one source of truth). An invalid
  candidate (`0` or `> 12` days) is rejected before it ever reaches flash;
  the previously committed config is untouched.
- `battery_capacity_mah` is persisted/read only. No SOC calculation, TX
  throttling, adaptive tracking, or solar logic reads it yet — infrastructure
  only, per the task's explicit scope.

## On-flash record format

`firmware/include/config_format.h` / `firmware/src/config_format.cpp`, a
sibling of `journal_format.h` (reuses its already-tested `crc32`/`put*`/`get*`
byte-order primitives directly, not its storage ownership, pages, or code
path):

```text
offset  size  field
0       4     magic ("ORC1" = 0x4F524331)
4       1     schema version (kVersion = 1); bytes 5-7 reserved, must be 0
8       8     generation (monotonic per ConfigStore instance; 0 is never valid)
16      2     encoded payload length (kPayloadSize = 8 for v1); bytes 18-19 reserved, must be 0
20      4     tracking_interval_seconds
24      4     battery_capacity_mah
28      4     CRC32 over bytes [0, 28)
32      4     commit word (kCommit = 0), programmed in a SEPARATE, LATER flash write
```

36 bytes total, comfortably under one 4,096-byte page, leaving room for
future schema growth without a layout redesign (matches the ADR's own
sizing estimate).

`decode()` fails closed (rejects the record, never guesses) on: bad magic,
unrecognized/newer version, nonzero reserved bytes, wrong payload length,
zero generation, or a CRC/commit mismatch — this is how "unknown/newer
schema must fail safely" and "torn/missing commit" are both satisfied by the
same one check.

## ConfigStore

`firmware/include/config_store.h` / `firmware/src/config_store.cpp`. Two
fixed pages, ping-ponged: a save always erases and writes the currently
**inactive** page (`target_page_ = active_page_ < 0 ? 0 : 1 - active_page_`),
so a failed or torn write can never corrupt the previously committed,
still-active page — `config()`/`ready()` stay on the last good commit
throughout. Mirrors `HistoryStore`'s proven invariant family (erase phase,
then body+CRC programmed, then the commit word programmed **separately,
last**, then a synchronous verify readback) but is a standalone sibling: no
shared code, state, or physical pages with `HistoryStore`/`journal_format`,
per the ADR's explicit instruction.

Recovery (`ConfigStore::begin()` → `recover()`) reads both pages, decodes
each, and keeps whichever decodes validly with the **higher generation**;
if neither decodes, `config()` falls back to the compile-time default and
`active_page_` stays `-1` (no committed page). Boot recovery is based only
on committed, `decode()`-valid flash content — never on any assumption about
what was "probably" in progress before a reset.

`requestSave()`:

- Rejects an invalid candidate outright (`diagnostics().rejected_candidates`),
  no flash touched, no state change.
- Accepts a candidate byte/semantically identical to the currently committed
  config as a **synchronous no-op** (`diagnostics().skipped_unchanged`) — no
  erase, no program, no generation bump.
- Otherwise starts an async erase→body/CRC→commit→verify sequence, advanced
  one physical flash step per `poll()` call, exactly like `HistoryStore`.
  `takeSaveResult()` reports completion (success/failure) once.

`requestReset()` is `requestSave(defaults)` — config reset therefore only
ever touches this one partition, through the same save path, with the same
"never corrupts the previously committed page on failure" guarantee. It
cannot reach history, security, or bond storage: `ConfigStore` only ever
holds a `FlashBackend&` scoped to the config region.

## FlashMutationGate generalization

M7P3's `FlashMutationGate` was history-region-specific (hardcoded
`storage_config::kBaseAddress`/`kRegionSize`, a single in-flight slot, a
single `Diagnostics`). The ADR requires config mutations to go through the
same single-flash-mutation-owner contract, so `FlashMutationGate` was
generalized to serve **exactly** History and Config — no speculative
Security/Bond client is added or queued, per the task's explicit instruction.

- **History's existing public API is completely unchanged**: `begin()`,
  `read()`, `program()`, `erasePage()`, `pollPending()`, `pumpEvents()`,
  `diagnostics()` — same signatures, same behavior. `firmware/tests/m7/test_m7p3_flash_gate.cpp`
  required **zero edits** and passes unchanged; this is the direct evidence
  that M7P3's history semantics were preserved, not just asserted.
- Config gets a parallel, symmetrical surface: `configPort()` returns a
  `FlashBackend&` (a private `ConfigPort` nested class) that `ConfigStore`
  holds exactly like `HistoryStore` holds its `FlashBackend&`, unaware the
  backend is shared. `NrfConfigFlash` (`firmware/src/nrf_config_flash.cpp`)
  is `NrfHistoryFlash`'s sibling for the config region's SoftDevice-disabled
  synchronous path — reuses `NrfHistoryFlash`'s exact linker-boundary
  readiness check (`__flash_arduino_end == storage_config::kBaseAddress`,
  the vendor linker script's fixed `FLASH` region end, unrelated to how much
  of the application is actually used) since that is one shared fact about
  the flash map, not something history-specific to duplicate incorrectly.
- **Single shared in-flight slot and single `pumpEvents()`.** Both clients
  get their own `Slot` (kind/target/staging/timing) and their own
  `Diagnostics`, but exactly one physical Nordic mutation is ever in flight
  (`in_flight_owner_`), and there is exactly one drain of the one global
  SoftDevice event queue. This is not incidental: two independent gate
  instances each calling `sd_evt_get()` would each blindly drain the *same*
  shared queue, and a client with an unaccepted (still-BUSY) submission would
  discard the *other* client's real completion event as "spurious" before it
  was ever observed — a genuine correctness hazard the M7P5 dual-client host
  test (`test_m7p5_flash_gate.cpp`) exercises directly (shared event-queue
  routing block).
- **Bounded admission, no heap**: exactly one outstanding request per
  client (2 total) plus the one in-flight operation — the same shape the
  ADR §10 describes ("at most one entry per request class plus the one
  in-flight operation"). When the physical slot is free and Config asks
  while History already has a request staged, Config stays queued rather
  than grabbing the slot — priority is enforced by admission order, not by
  interrupting an already-accepted physical operation (the Nordic SVCs have
  no cancel). Covered by `test_m7p5_flash_gate.cpp`'s two dedicated priority
  blocks, including the case where Config asks *before* History in program
  order but History is still admitted first.
- **Async source-buffer lifetime, timeout (4s), BUSY-retry, and error
  semantics are unchanged** from M7P3 — the same staging-copy-before-submit
  pattern, the same wall-clock timeout (not a fixed attempt count), just
  applied per-`Slot` instead of per-gate.
- `NrfHistoryFlash` itself is **not modified at all** in this slice (zero
  diff), matching "do not weaken NrfHistoryFlash guards."

## Runtime integration

`GnssManager` gained a runtime `tracking_interval_ms_` member (default
`gnss_config::kTrackingIntervalMs`, reset to that default by every `begin()`)
and `setTrackingIntervalMs(uint32_t)`/`trackingIntervalMs()`. The two call
sites that previously used the compile-time `gnss_config::kTrackingIntervalMs`
constant for scheduling (`startAcquisition()`, `enterLowPower()`) now use
`tracking_interval_ms_` instead — nothing else in `GnssManager` changed: the
acquisition timeout, fresh-fix age bound, short-interval continuous-tracking
policy, and all GNSS power/acquisition behavior are untouched, still driven
by their own unchanged `gnss_config` constants.

`setTrackingIntervalMs(0)` is ignored (keeps whatever interval was already in
effect) — a defensive guard so a somehow-zeroed candidate can never reach the
scheduler, on top of `ConfigStore`'s own candidate validation.

`main.cpp`: `config_store.begin()` runs before `gnss_manager.begin()`, and
`gnss_manager.setTrackingIntervalMs(config_store.config().tracking_interval_seconds * 1000UL)`
runs immediately after `gnss_manager.begin()` (which itself resets the
interval to the compile-time default) — so the very first acquisition
schedule already reflects durable config, and a `config_store.begin()`
failure still yields the safe 180s default (see "On-flash record format"
above: the default is set before recovery ever touches flash). `loop()`
calls `history.poll()` before `config_store.poll()` each tick (history's
live store-before-send outranks config writes — both by this call order and
by the gate's own internal admission priority), and one shared
`storage_flash_gate.pumpEvents()` drains both clients' events.

No changing-interval-mid-acquisition hazard exists: the interval is only
read when computing the *next* due point (`startAcquisition()`/
`enterLowPower()`); it never touches `acquisition_started_at_ms_` or the
timeout check, so it cannot create overlapping acquisitions. Covered
directly by `test_m7p5_gnss_interval.cpp`'s
`testIntervalChangeDuringAcquisitionDoesNotOverlap`.

**No serial/BLE command surface to change config values was added in this
slice** — `ConfigStore::requestSave()`/`requestReset()` are infrastructure
APIs for a future BLE/serial configuration milestone (M7P7+) to call. Nothing
in shipped firmware currently calls them; only host tests exercise the save
path directly.

## Independent/self-review

A local `/code-review high` self-review pass on this diff (**not** the cloud
multi-agent `/ultrareview` — that requires user-triggered billing this
session cannot invoke on its own, and is not claimed here) found five
issues. Four were fixed and re-validated; one was reviewed and intentionally
left as-is, recorded below rather than silently dropped:

1. **`ConfigStore::recover()` trusted a structurally-sealed but semantically
   out-of-range recovered record.** A record with correct magic/CRC/commit
   could still carry a `tracking_interval_seconds` outside
   `gnss_config::kMaxTrackingIntervalSeconds` (e.g. written by a future
   firmware with a wider bound, then read back by this one). Fixed by
   reusing the same `validCandidate()` check `requestSave()` already uses
   inside `recover()`; a recovered-but-invalid record is now treated as
   corrupt (counted in `diagnostics().recovery_corruptions`) instead of
   adopted.
2. **`config_store.poll()` was not gated by `!radio_manager.isTransmitting()`**
   the way `history.poll()` already is, so config could win admission into
   `FlashMutationGate`'s shared in-flight slot during a TX window where
   history is intentionally prevented from even asking — contradicting this
   document's own priority claim and, once SoftDevice is enabled, creating a
   real (if narrow) window where history has to wait behind a config write.
   Fixed by moving `config_store.poll()` inside the same
   `if (!radio_manager.isTransmitting())` block as `history.poll()` in
   `main.cpp`, for the same underlying reason that guard exists in the first
   place (a synchronous flash op must not run during TX).
3. **A spurious SoftDevice flash event with no client currently in flight
   was always attributed to history's diagnostics**, even when config was
   the client that had just released the slot. Fixed by adding
   `FlashMutationGate::last_owner_` (set whenever a client is admitted,
   preserved across release) and routing that specific spurious-event case
   to `diag(last_owner_)` instead of hardcoding history — a
   diagnostics-only fix, no functional behavior change.
4. **Stale class comment.** `flash_backend.h`'s `NrfConfigFlash` comment
   claimed it does *not* reuse `NrfHistoryFlash`'s exact
   `__flash_arduino_end == kBaseAddress` readiness check — true of an
   earlier draft, but `nrf_config_flash.cpp`'s actual `begin()` deliberately
   *does* reuse that exact check (see "FlashMutationGate generalization"
   above for why that is correct, not a shortcut). Fixed the comment to
   match the real, correct implementation instead of leaving a misleading
   claim for a future reader.
5. **`battery_capacity_mah` has no validation beyond fitting in `uint32_t`.**
   Reviewed and left as-is: the field has no consumer yet (explicit task
   scope — "DO NOT use it yet for ... any power-policy change"), so an
   arbitrary value is inert today; the task specified no capacity range;
   and adding one now risks rejecting a legitimate future large-pack value
   with an invented limit. Revisit once a real consumer (SOC/power policy)
   is implemented and can state its own actual bound.

All fixes re-validated: host tests **40/40 PASS** (unchanged count),
`pio run -e rak4630` **SUCCESS** (RAM 14,828 B unchanged, flash +48 B from
the pre-fix build).

## Independent-audit review (PR #15) — closure

An independent audit review posted on PR #15 — separate from, and after,
the self-review pass above — found four issues. All four are fixed on this
branch, re-validated, and documented here; PR #15 remains **not merged**.

1. **BLOCKER — `FlashMutationGate` queued-timeout semantics.**
   `Slot::started_ms` was set when a request was first *staged*
   (`program()`/`erasePage()`), before M7P5's admission queue existed to
   make a client wait behind the other one. Once queuing was introduced, a
   request could legitimately wait longer than `kOperationTimeoutMs` (4s)
   for admission, then finally be admitted and have `sd_flash_*` genuinely
   start — but `submitOrRetry()`'s timeout check still measured elapsed
   time from the original staging timestamp, so the request could be failed
   closed on the very first poll after admission, before the physical
   operation had any real chance to complete.

   Fixed by adding `Slot::admitted` (`firmware/include/flash_mutation_gate.h`)
   and moving the `started_ms` assignment out of `program()`/`erasePage()`/
   `programConfig()`/`erasePageConfig()` and into `submitOrRetry()`
   (`firmware/src/flash_mutation_gate.cpp`): the timeout deadline base is
   now set exactly once, the first time a request transitions from queued
   to actually holding the shared in-flight slot (`admitted` false → true),
   never at staging time. A request that waits arbitrarily long in the
   admission queue always gets a full, fresh `kOperationTimeoutMs` budget
   once genuinely admitted. `releaseSlot()` resets `admitted` so a reused
   `Slot` starts the next request's clock correctly. The bounded timeout
   itself is unchanged (still exactly `kOperationTimeoutMs`, still
   wall-clock-scaled, not a fixed attempt count) — only *when* it starts
   changed.

   Regression coverage added to `firmware/tests/m7/test_m7p5_flash_gate.cpp`:
   one block has History own the physical slot while Config stages and
   waits >4000ms purely queued (no false timeout, `write_calls` proves no
   submit attempt while queued), History completes, Config is admitted and
   given a verified fresh ~4000ms budget, and completes successfully with
   no misattributed event and no overlapping ownership (`write_calls`
   strictly serializes: 1 during History, 2 only after History releases).
   A second, symmetric block repeats this with History queued behind
   Config's in-flight operation.

2. **`ConfigStore` stale completion result.** `requestSave()` only checked
   `busy()`, which becomes false the instant `poll()` finishes a save
   (`finishSave()`/`fail()` both clear `job_`) — regardless of whether the
   caller had read that save's result via `takeSaveResult()` yet. A second
   `requestSave()` could therefore start save B before save A's result was
   consumed, and a later `takeSaveResult()` would then return save B's
   outcome to a caller that believed it was still waiting on save A.

   Fixed with a small fail-closed ownership rule in `requestSave()`
   (`firmware/src/config_store.cpp`): if `save_result_ready_` is still true
   (a prior async save's result has not been consumed), a new save is
   refused (`++diagnostics_.blocked_pending_result; return false;`) rather
   than started. No queue or generic command framework was added — this is
   a single boolean check ahead of the existing `startSave()` call. The
   synchronous unchanged-config no-op path (`skipped_unchanged`) is
   deliberately unaffected by this rule and documented as such in
   `config_store.h`: it never arms `save_result_ready_`, so it can never
   collide with a pending result and must keep succeeding even while one is
   unread.

   Regression coverage added to `firmware/tests/m7/test_m7p5_config_store.cpp`
   (blocks 14–15): block 14 lets save A settle without reading its result,
   confirms a differing save B is refused
   (`diagnostics().blocked_pending_result == 1`) and does not disturb the
   config A already committed, then confirms consuming A's result unblocks
   the store and B's own subsequent result is unambiguously B's (not a
   stale A leftover, and A's result cannot be taken twice). Block 15
   confirms the synchronous no-op path still succeeds while a prior async
   result sits unread, and that a genuinely different candidate is still
   correctly blocked in the same state.

3. **Recovery regression test.** The self-review above (finding 1) already
   added `validCandidate()` re-validation inside `recover()`, but had no
   test that directly constructs a structurally-sealed (correct
   magic/version/length/generation/CRC/commit — i.e. `decode()`-valid)
   record whose payload is semantically out of range. Added directly to
   `firmware/tests/m7/test_m7p5_config_store.cpp` (blocks 16a/16b):

   - 16a: a single page holds such a record (via `config_format::encode()`
     directly, bypassing `requestSave()`'s own validation, since a record
     could reach flash this way from a future firmware with a wider
     bound); the other page is erased. Recovery rejects it
     (`diagnostics().recovery_corruptions >= 1`) and falls back to
     defaults (180s / 0), exactly like any other corrupt/absent page.
   - 16b: page 0 holds a real, previously-committed valid save (generation
     1); page 1 is then directly poked with a structurally sealed but
     semantically invalid record at a *higher* generation (2). Recovery
     must reject page 1 despite its higher generation and keep page 0's
     valid, lower-generation config — proving the semantic check is
     applied before generation comparison can let an invalid record win.

4. **Documentation truth.** `docs/architecture/ORUN_CURRENT_ARCHITECTURE_RULES.md`
   stated the code was last reviewed against
   `main@8b44d9b9a96bcf7eea6dc494b807b62b43a7ea12` "(M7P5 durable config
   store merged...)". That SHA is `8b44d9b`, the M7P4 bond-storage merge
   commit (`git log` confirms) — it is the baseline M7P5 branches from, not
   a commit containing M7P5. Fixed the wording (top status block and the
   §9 partition-plan paragraph) to state accurately that this SHA is the

## Limitations

- **HOST PASS != PHYSICAL PASS.** `ConfigStore`'s SoftDevice-enabled
  asynchronous save path (through the generalized `FlashMutationGate`) has
  not been exercised on real hardware — nothing in this slice enables
  SoftDevice. Software/build validated; SoftDevice-enabled physical
  config-flash mutation not yet physically validated. This mirrors M7P3's
  own unresolved physical-validation status for history's async path, and
  is not a new or additional physical gap — the same eventual M7P7
  SoftDevice-enable slice will need to validate both together.
- No physical power-cut/brownout test was performed at any real config
  commit point; the "torn write" tests are deterministic host-side fault
  injection (a fake `FlashBackend` that reports `kFailed`/`kPending` on
  cue, or a memory snapshot taken mid-write), not an electrical test.
- No user-facing command interface (serial or BLE) to change
  `tracking_interval_seconds`/`battery_capacity_mah` exists yet;
  `ConfigStore`'s save/reset APIs are infrastructure for a future milestone.
- `battery_capacity_mah` has no consumer yet by design (explicit task
  scope) — persisted and round-tripped, not used for any power decision.
