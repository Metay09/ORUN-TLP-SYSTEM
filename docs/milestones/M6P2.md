# M6P2 — 10-second TRACKER post-TX RX window

Status: **IMPLEMENTATION PREPARED; HOST/BUILD/HARDWARE VALIDATION PENDING.**

Baseline: `main@868b622cd07e3fe018b9f612ebc4455819a53e4f` (PR #24 merged).
Branch: `feat/m6p2-tracker-rx-window-10s`.

## Owner decision

On 2026-09-20 the product owner selected **10 seconds** as the current
development default for the bounded TRACKER post-TX LoRa receive window.

This is a deliberate availability-versus-energy tradeoff. It is intended to
leave practical rendezvous headroom after the existing 1200–4200 ms uplink
relay scheduling delay. It is not a measured battery-life optimum and is not a
guarantee that an as-yet-undefined secure downlink/ACK format will fit.

## Runtime change

`firmware/include/radio_config.h`:

```cpp
kWindowedRxAfterTxMs: 3000 -> 10000
```

No state-machine rewrite is required. The existing M6P1 invariant remains:

- a local TX terminal completion opens one fixed window;
- RX activity/error/timeout may restore RX only inside that existing deadline;
- RX does not extend the deadline;
- deadline expiry sleeps a windowed TRACKER;
- relay-forwarding-enabled and application-receiving nodes remain continuous RX;
- a local TX from sleep still wakes the radio and opens a fresh window after
  terminal completion.

## Timing rationale

Current canonical M5 figures at SF11/BW125/CR4/5/preamble 8:

- POSITION airtime: 987.136 ms;
- RELAY_FORWARD airtime: 1232.896 ms;
- uplink relay scheduling delay: 1200–4200 ms.

A worst-case currently scheduled relayed uplink can therefore finish at a
gateway at approximately:

```text
4.200 s + 1.232896 s = 5.432896 s
```

after TRACKER TX completion.

With a 10-second TRACKER window this leaves approximately:

```text
10.000 s - 5.432896 s = 4.567104 s
```

for future gateway processing and a possible return path. That remaining time is
engineering headroom only; no downlink packet or reverse forwarding runtime
exists today.

## System impact

| Area | Impact |
| --- | --- |
| TLP v1 bytes / golden fixtures | unchanged |
| Relay forwarding / dedupe | unchanged |
| RF frequency/SF/BW/CR/power | unchanged |
| BASE / relay-enabled RX policy | unchanged, continuous |
| TRACKER RX after local TX | changed from 3 s to 10 s |
| Storage / identity / sequence | unchanged |
| GNSS / activity / geofence | unchanged |
| BLE / flash ownership | unchanged |
| Security / ACK / commands | no new implementation |
| Power | TRACKER SX1262 RX stays active ~7 s longer after each local TX; quantitative current impact not measured |

The energy cost scales with actual local TX cadence. The current 3-minute GNSS
tracking interval is a development default, so this setting must not be used to
claim production battery life.

## Tests

Existing M6P1 state-machine tests derive their deadlines from
`kWindowedRxAfterTxMs`, so they exercise the same rollover/sleep/no-extension
logic at 10 seconds. M6P2 additionally locks the owner-selected exact default
with a host assertion:

```cpp
assert(radio_config::kWindowedRxAfterTxMs == 10000);
```

Required before merge:

1. full `./firmware/tests/run_host_tests.sh`;
2. `pio run -e rak4630`;
3. review warnings and binary-size delta.

Because this changes real TRACKER radio-on time/power behavior, physical
validation should then confirm one TRACKER post-TX window remains open before
10 s and transitions to ASLEEP at/after the configured deadline. That hardware
check validates timing/state behavior only; without current-measurement
instrumentation it does not validate energy consumption.

## Non-claims

M6P2 does not implement or prove:

- gateway ACK/contact;
- gateway->relay->tracker downlink;
- selected reverse relay runtime;
- multi-gateway coordination;
- authenticated network contact;
- command delivery/result;
- quantitative current draw or battery life.

The historical M6P1 3000 ms physical evidence remains evidence for that older
tested image only.
