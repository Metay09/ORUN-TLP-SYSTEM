# M7P4 — Relocate BLE bond InternalFS into its reserved flash partition

Status: **HOST PASS; BUILD PASS; NORMAL SHIPPED FIRMWARE UNCHANGED (byte-for-byte
identical RAM/Flash to M7P3); NO BLE RUNTIME; NO PHYSICAL BLE VALIDATION.**

Baseline: `main@422735cba54ff30d49fff2c91d5d1b3366d661aa` (M7P3 merged).
Branch: `feat/m7p4-relocated-bond-storage`.

## Purpose

M7P1 decided, and M7P2 reserved, a BLE bond partition at
`0x0EB000..0x0ED000`. M7P4's scope is deliberately narrow: relocate the
stock Adafruit nRF52 `InternalFS`/LittleFS backend — the thing Bluefruit's
`bond_init()` uses for BLE bond storage — away from its default location
(which is the exact same pages as the ORUN history journal) and into that
reserved partition. **This slice does not enable BLE.** `Bluefruit.begin()`
is not called anywhere in shipped firmware; no advertising, pairing,
provisioning, or DFU code is added.

## `patch_internalfs.py`

New `firmware/scripts/patch_internalfs.py`, following the exact fail-closed,
pinned-source, auto-restoring idiom already proven twice in this repo
(`patch_wire.py` for R4, `patch_radio.py` for R2.1):

- Verifies `package.json` version `== "1.10700.0"` before doing anything.
- `transform(source)` is a pure function: rejects any input whose Git blob
  SHA does not exactly equal the pinned `923aede3cd736ac4a7caf75fed982aeb2c726136`;
  replaces `LFS_FLASH_ADDR`'s and `LFS_FLASH_TOTAL_SIZE`'s definition lines
  **exactly once each** (`replace_once`, matching `patch_wire.py`'s own
  helper) — a missing or duplicated target definition raises, never silently
  patches the wrong occurrence or none at all.
- `apply(core)` mirrors `patch_wire.py`'s exact recovery logic: if the
  on-disk file already starts with the ORUN marker, it re-derives the patch
  from the backup and requires the result to match byte-for-byte (idempotent
  re-apply, and fail-closed recovery from an interrupted prior build); a
  missing or mismatched backup raises rather than guessing. `apply()` was
  refactored to **return** the `restore()` closure (a small, test-motivated
  change from `patch_wire.py`'s pattern of registering `atexit` internally)
  so tests can call it directly without waiting on process exit; the real
  invocation at the bottom of the file still does
  `atexit.register(apply(core))`, identical behavior to the established
  pattern.
- Does not patch `bonding.cpp`, does not invent a bond file format, does not
  touch any file outside `InternalFileSystem.cpp`.

```ini
extra_scripts =
    pre:scripts/check_storage_layout.py
    post:scripts/patch_wire.py
    post:scripts/patch_radio.py
    post:scripts/patch_internalfs.py
```

Ordering was **verified against the actual installed PlatformIO source**
(`~/.local/pipx/venvs/platformio/lib/python3.11/site-packages/platformio/builder/main.py`),
not assumed from the `pre:`/`post:` naming alone:

```text
line 167: env.SConscript(env.GetExtraScripts("pre"), exports="env")   # check_storage_layout.py
line 173: env.SConscript("$BUILD_SCRIPT")                             # framework/board setup only
line 180: env.SConscript(env.GetExtraScripts("post"), exports="env")  # patch_wire/patch_radio/patch_internalfs
```

All of this happens during SCons environment/DAG *construction*, before any
`.o` is actually compiled (compilation happens later, when SCons executes
the accumulated Builders). This confirms the intended sequence holds:
`check_storage_layout.py`'s pre-build audit reads genuinely stock upstream
source first; `patch_internalfs.py` relocates it next; only then does actual
compilation use the patched content; `check_exclusive_owner`/
`check_application_ceiling` (registered via `env.AddPostAction` during the
`pre:` phase, but *executed* after linking) inspect the final linked ELF
last. The pre-build source audit is **not weakened** — it still requires
genuinely-stock content in the normal case (see next section for the one
narrow, backup-verified exception).

## Build guard changes (`check_storage_layout.py`)

**Pre-build audit** (`required` list): unchanged in spirit, with one narrow
addition for robustness. It still requires the linker text, `flash_nrf5x.h`
page size, and `BOOTLOADER_ADDR` to match exactly as before. For
`InternalFileSystem.cpp` specifically, it now accepts *either* the exact
stock definitions *or* a **provably valid** M7P4-relocated file left over
from an interrupted prior build — "provably valid" meaning: `relocation_ok()`
(imported from `patch_internalfs.py`, not duplicated) returns true *and* a
matching `.orun-original` backup exists whose blob hash equals the pinned
upstream SHA. Anything else (including a merely marker-bearing but
otherwise-wrong file) still fails the build. This exists so a single
interrupted build cannot permanently brick subsequent builds by leaving the
audit unable to recognize its own patch script's own valid, recoverable
state — the same fail-closed philosophy `patch_internalfs.py`'s own
`apply()` already uses, reused rather than reimplemented.

**Post-link ownership check** (`check_exclusive_owner`): the previous
unconditional "`InternalFS` symbol present -> fail" rule is replaced with a
three-way distinction, exactly as required:

```text
A. stock InternalFS / wrong range linked         -> FAIL
B. correctly M7P4-relocated InternalFS linked    -> PASS (partition-overlap check satisfied)
C. unknown/vendor-drifted InternalFS linked      -> FAIL
```

Implementation: if the `InternalFS` symbol is present in the linked ELF, the
script re-reads the **actual on-disk vendor source** at that moment (still
in its patched state — `patch_internalfs.py`'s `atexit` restore has not run
yet, since post-link actions execute within the same PlatformIO process) and
calls the same `relocation_ok()` used by the pre-build audit and by
`patch_internalfs.py` itself. `flash_nrf5x_write`/`flash_nrf5x_flush`
linkage is now permitted **only** when `InternalFS` is also linked (they are
InternalFS's own internal driver primitives; nothing else in this codebase
calls them) — their presence *without* `InternalFS` linked remains an
error, unchanged from before. The M7P2 application-ceiling guard
(`check_application_ceiling`) is untouched and remains fully active.

**Normal shipped build**: `InternalFS` is never linked (nothing references
it), so this entire new distinction is inert dead code for the actual
product firmware — verified, not assumed (see ELF verification below).

## M7P3 flash-ownership contract — explicit, not hidden

**Relocation alone does not make `InternalFS` participate in the M7P3
`FlashMutationGate` single-flash-mutation-owner contract.** Inspected
`flash_nrf5x.c` directly (unmodified by this patch — M7P4 only touches
`InternalFileSystem.cpp`'s two `#define`s):

- `fal_erase`/`fal_sub_program` call `sd_flash_page_erase`/`sd_flash_write`
  **directly**, with their own bounded (≤20 attempt) retry loop — not
  through `FlashMutationGate`.
- Completion is awaited via `wait_for_async_flash_op_completion()`, which
  blocks the calling task on a FreeRTOS semaphore (`xSemaphoreTake(_sem,
  portMAX_DELAY)`) fed by `flash_nrf5x_event_cb()`.
- `flash_nrf5x_event_cb()` is only ever invoked from **Bluefruit's own**
  SoftDevice event-processing task (`bluefruit.cpp:711`,
  `if (flash_nrf5x_event_cb) flash_nrf5x_event_cb(soc_evt);`) — confirmed
  identically to the M7P3 finding, since this call site is untouched.

So: relocated `InternalFS` still has its own, entirely separate SoftDevice
flash-mutation path, independent of `FlashMutationGate`, and its own
independent SoftDevice event consumption, independent of
`FlashMutationGate::pumpEvents()`. This is **not hidden** and BLE is **not**
being enabled to paper over it. It is recorded below as an explicit,
unresolved M7P7 prerequisite, exactly as instructed.

## Unresolved M7P7 integration points

Recorded explicitly, not hidden, exactly as instructed:

1. **SoftDevice event-pump ownership.** `FlashMutationGate` (M7P3) pumps
   `sd_evt_get()` itself, directly, independent of Bluefruit. Stock
   `InternalFS`/`flash_nrf5x.c` (M7P4-relocated, but otherwise unmodified)
   has its **own** independent event consumption via Bluefruit's own event
   task (`flash_nrf5x_event_cb`, only invoked from `bluefruit.cpp`'s event
   processing). If a future slice starts Bluefruit while `FlashMutationGate`
   is also live, both would compete for the same global SoftDevice event
   stream (`sd_evt_get` drains a single shared queue). M7P4 does not create
   a second *active* event pump — `InternalFS`'s own pump only becomes live
   once `Bluefruit.begin()` actually runs, which nothing in this slice does
   — but this remains a real, unresolved architectural question for M7P7.
2. **`InternalFS`/`flash_nrf5x` participation in the single flash-mutation
   contract.** Confirmed by source inspection (see "M7P3 flash-ownership
   contract" above): relocated `InternalFS` still calls `sd_flash_write`/
   `sd_flash_page_erase` directly, bypassing `FlashMutationGate` entirely.
   M7P3's "at most one flash mutation in flight" invariant is therefore
   **not** actually unified across `HistoryStore` and BLE bonds yet — it
   only covers `HistoryStore`. This must be resolved (either by making
   `InternalFS`'s driver route through `FlashMutationGate`, or by an
   explicit, reviewed arbitration model between the two independent paths)
   before `Bluefruit.begin()` is safely called in a slice that also has
   `HistoryStore` active concurrently.

## Independent/self-review

Local `/code-review high` self-review only (**not** the cloud multi-agent
`/ultrareview` — requires user-triggered billing this session cannot invoke
on its own). Recorded here regardless of outcome, per the task's own
instruction not to skip this step.

Three findings, all fixed and re-validated:

1. **`relocation_ok()` logic gap.** The check only asserted the old
   `LFS_FLASH_ADDR` line was absent, not the old `LFS_FLASH_TOTAL_SIZE` line
   — a source file carrying both new definitions *and* the stale 7-page size
   line would have incorrectly passed as validly relocated. Fixed by adding
   `and OLD_SIZE_LINE not in source_text` to the boolean expression in
   `patch_internalfs.py`; both stock lines must now be absent, not just one.
2. **Host test hard-depended on the real installed framework package.**
   `test_m7p4_patch_internalfs.py` originally asserted
   `REAL_INTERNALFS.exists()` and aborted the whole host suite
   (`set -euo pipefail`) on any checkout that hasn't already run `pio run`
   for `rak4630` — including a fresh clone or CI runner. Fixed by adopting
   `tests/r4/test_patch_wire.py`'s established pattern: a self-contained
   inline `FIXTURE` string stands in for the upstream file, with
   `ORIGINAL_GIT_BLOB_SHA` overridden to `git_blob_sha(FIXTURE)` so the test
   needs no installed package at all. The real installed file (present in
   this dev environment) is still cross-checked against the script's actual
   pinned hash, but only as a non-fatal bonus assertion that reports and
   skips gracefully when the package isn't present, rather than a hard
   requirement.
3. **Duplicated backup-path literal across three call sites.**
   `check_storage_layout.py` independently hardcoded
   `libraries/InternalFileSytem/src/InternalFileSystem.cpp[.orun-original]`
   in three places instead of sourcing it from `patch_internalfs.py`. Fixed
   by adding `RELATIVE_TARGET_PATH`/`RELATIVE_BACKUP_PATH` constants and a
   `target_and_backup_paths(core)` helper to `patch_internalfs.py` (also
   used by its own `apply()`), and updating `check_storage_layout.py` to
   call it once and reuse the result at all three sites.

After all three fixes: full host suite re-run (**36/36 PASS**, unchanged
count), `pio run -e rak4630` re-run (**SUCCESS**, RAM 14,564 B / Flash
148,352 B, unchanged from the pre-fix build since all three fixes are
Python-script-only), real installed `InternalFileSystem.cpp` re-verified
restored to `923aede3cd736ac4a7caf75fed982aeb2c726136`, `git status`/`git
diff --check` re-checked clean. No new findings surfaced a need for a
fourth review pass.
