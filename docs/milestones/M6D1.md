Branch: `feat/m6d1-geofence-operational-state`.

## Purpose

M6D1 adds the smallest pure state owner needed before production GNSS/runtime
composition.

It deliberately does **not** wire geofence into `main.cpp`, GNSS scheduling,
PositionFlow, RF, flash, BLE, backend or secure EVENT transport.

Inputs are already accepted `PermittedAreaRelation` values from the existing
M6C geometry/runtime boundary.

## Frozen behavior in this slice

Product-visible confirmed states remain:

```text
INSIDE
OUTSIDE
```

The machine also has an internal unclassified condition after construction,
reset, reboot or authoritative area-set replacement. It is not a third
user-visible geofence state.

### Initial classification

- BOUNDARY while unclassified -> remain unclassified;
- first INSIDE -> establish INSIDE immediately;
- first OUTSIDE -> start the same bounded 3-observation confirmation used for
  INSIDE -> OUTSIDE;
- two early OUTSIDE votes still do not finish early; the intended full
  three-observation set is consumed.

This biases initial behavior against false OUTSIDE alarms without paying a
three-fix burst for the normal clearly-inside boot case.

### Transition confirmation

For an apparent INSIDE <-> OUTSIDE transition:

- candidate observation is evidence #1;
- at most two more accepted relations are consumed;
- exactly three evidence slots complete the episode;
- 2-of-3 INSIDE/OUTSIDE majority decides;
- no early completion after two matching votes;
- failure to obtain a transition majority leaves the previous confirmed state
  unchanged.

### BOUNDARY

BOUNDARY is geometry evidence but not a third operational state.

- it never starts a transition episode by itself;
- inside an already-started episode, it consumes one of the maximum three
  evidence slots;
- it contributes neither an INSIDE nor OUTSIDE vote.

This keeps confirmation bounded and fail-safe at the fence edge.

### Invalid assessment

`kInvalidPoint` and `kInvalidAreaSet` are rejected by the operational
machine and do not consume the three-observation budget. The geometry/runtime
owner remains responsible for producing valid assessment input.

### Timeout / failure

M6D1 does not choose the real GNSS confirmation deadline. The later acquisition
owner calls `abortConfirmation()` when its bounded deadline/retry budget is
exhausted.

Abort:

- preserves the prior confirmed state if one exists;
- remains unclassified if no state had yet been established;
- emits no transition/event;
- returns to base cadence policy.

Exact timing belongs to M6D2 because it depends on the existing GNSS single-owner
schedule and no-overlap constraints.

### Reboot / config replacement

Operational state is runtime-only in M6D1. There is no new flash owner.

Construction/reset starts unclassified at base cadence. A future production
area-set replacement must reset old geometry evidence before evaluating fresh
Location against the new set, matching
`ORUN_GEOFENCE_OPERATIONAL_POLICY.md`.

This intentionally chooses **no operational-state persistence for the first M6D
implementation**. Reboot therefore cannot resurrect a stale OUTSIDE/INSIDE
decision from old geometry/configuration.

### Cadence output

The pure machine exposes policy only:

```text
unclassified / INSIDE -> base B
confirmed OUTSIDE      -> B / 3 policy
```

It does not calculate milliseconds, minimum interval, rounding or re-anchor the
GNSS schedule. Those are M6D2 responsibilities.

### OUTSIDE event occurrence

`kConfirmedOutside` is emitted only on the one confirmed transition into
OUTSIDE. Repeated OUTSIDE observations return stable OUTSIDE and do not create a
second occurrence.

No RF EVENT packet is introduced. Secure remote OUTSIDE delivery remains a later
EVENT/v2 dependency.

## Ownership

```text
M6C geometry/runtime        -> polygon validation + relation
M6D1 operational state     -> confirmation + confirmed INSIDE/OUTSIDE
future M6D2 integration    -> accepted Location feed + deadline + GNSS cadence
future Event service       -> durable/secure OUTSIDE event lifecycle
```

M6D1 does not read raw GNSS, call `GnssManager`, write ConfigStore/HistoryStore,
or send radio packets.

## Explicitly deferred to M6D2

Before production runtime integration:

- exact confirmation deadline/retry timing;
- representative real fix selection from the winning majority;
- `B / 3` integer/minimum rule;
- safe schedule re-anchor when B <-> B/3 changes;
- interaction with an acquisition already in progress;
- accepted Location -> M6C -> M6D1 composition;
- focused GNSS/geofence physical validation.

## Compatibility / expected non-impact

```text
TLP v1 bytes:                 unchanged
RF / relay behavior:          unchanged
GNSS runtime/power:           unchanged
History / Config / Security:  unchanged
BLE / DFU:                    unchanged
Role / identity:              unchanged
main.cpp production wiring:   unchanged
```

The new source may compile into the firmware build graph, but without composition
root use it must not create active product behavior.
