## Purpose

M6D2 connects the existing accepted fresh GNSS Location path to M6C bounded
geofence geometry and M6D1 operational confirmation without changing TLP v1
bytes, RF settings, persistent geofence state, BLE ownership or secure EVENT
transport.

The slice adds only the runtime composition needed to:

- classify already accepted fresh Location observations;
- obtain at most two extra observations in the same GNSS acquisition after a
  transition candidate;
- keep the original GNSS acquisition timeout as the outer ceiling;
- apply an exact 10 s geofence confirmation deadline from the first candidate;
- select one real winning-majority fix as the representative position;
- preserve store-before-send for the representative fix;
- change runtime cadence between configured base `B` and derived `B / 3`;
- re-anchor cadence from confirmation completion without catch-up bursts;
- abort fail-safe on deadline, session/recovery boundary, invalid geometry
  ownership or continuation rejection.

## Frozen M6D2 behavior

### Confirmation deadline

The first transition candidate starts a 10,000 ms confirmation deadline.
The owner loop checks the deadline before GNSS service, and the coordinator also
checks each accepted observation's own `captured_at_ms` before it can consume
evidence. A GNSS poll which itself crosses the deadline therefore cannot let a
late observation decide the transition.

This deadline does not replace the existing R3 GNSS acquisition ceiling.
Additional observations remain inside the same acquisition/session owner and
never increment the normal acquisition-attempt counter. If the original
120-second acquisition ceiling is reached first, confirmation aborts and the
previous confirmed state remains authoritative.

### Additional GNSS observations

`GnssManager::continueCurrentAcquisitionForAdditionalFix()` is legal only after
the current fresh fix has been consumed and while the manager still owns the
same successful acquisition context.

It:

- does not power-cycle GNSS;
- does not increment `session_generation_`;
- does not increment acquisition attempts;
- does not restart the original acquisition timeout;
- rejects overlap/resync/configuration-conflict states;
- requires one explicit continuation request per additional observation.

At most two extra accepted observations are requested by M6D1's bounded
three-slot confirmation episode.

### Representative fix

The completed majority never synthesizes an averaged coordinate.

The representative must be one of the real accepted observations belonging to
the winning INSIDE/OUTSIDE majority. Deterministic tie-break:

1. lower HDOP;
2. more satellites;
3. later observation index.

This uses only quality metadata already present on accepted `GnssFix`; no new
accuracy field or quality contract is invented.

### Normal slot 0 versus representative POSITION

The candidate which starts a confirmation episode is still the ordinary
scheduled POSITION (slot 0), so it enters the existing PositionFlow
store-before-send path once. The two additional confirmation observations are
evidence-only and are not independently stored/transmitted as normal POSITIONs.

If the winning representative later resolves to that same slot 0 and its normal
PositionFlow admission succeeded, M6D2 reuses that already-owned logical
POSITION instead of allocating a second sequence/history record/TX for identical
GNSS data. If slot 1 or slot 2 is selected, that real accepted observation is
queued once as the representative through PositionFlow.

### Storage and live freshness

A representative observation may wait behind an already in-flight HistoryStore
append.

M6D2 therefore distinguishes:

- **historical validity**: the already accepted real observation is still stored;
- **live validity**: PositionFlow's existing 5-second freshness gate still
  suppresses live RF transmission if the observation has aged out before
  storage completes.

This closes a review finding where an accepted OUTSIDE representative could
otherwise have been dropped entirely merely because flash admission took longer
than the live-freshness window.

Store-before-send remains unchanged.

### Cadence

`INSIDE/unclassified -> B`

`confirmed OUTSIDE -> ceil(B / 3)` in whole seconds.

The derived cadence is runtime-only and never overwrites ConfigStore's durable
base interval. M6D2 derives it from the **base interval actually applied to
GnssManager at boot**, not from a newer ConfigStore value which M7P5 has not
otherwise applied mid-session.

Schedule re-anchor occurs from the completion point, avoiding both an immediate
catch-up acquisition and waiting on the previous cadence.

With the current development default `B = 180 s`, OUTSIDE derives to `60 s`.
The existing GNSS policy deliberately keeps GNSS continuously powered for
intervals `<= 60 s`. M6D2 does not hide or override that existing policy.
Therefore confirmed OUTSIDE currently means substantially higher GNSS power
use than normal 180-second tracking. This remains a field/power validation item;
no battery-life claim is made.

### Event boundary

A real confirmed INSIDE -> OUTSIDE transition creates one local semantic
occurrence only.

M6D2 does **not** add a TLP v1 alarm packet. Remote geofence alarm delivery
remains gated on the reviewed secure EVENT/v2 lifecycle. Initial/reboot
`kInitializedOutside` does not create a physical-crossing event.

### Production geofence configuration

No production polygon is hard-coded.

The normal production image leaves the geofence coordinator unconfigured until
a future reviewed durable geofence resource owner supplies an authorized area
set.

A separate `rak4630_m6d2_geofence_probe` target exists only for physical
qualification. It derives a temporary small rectangle around the first accepted
GNSS fix and must never be used as deployed firmware. Probe diagnostics now log
the effective cadence interval/power-policy implication and explicitly state
that the existing `GNSS FIX ttff=` field is total acquisition age, not
inter-fix latency.

## Compatibility / ownership

```text
TLP v1 bytes / golden fixtures: unchanged
RF frequency/SF/BW/CR/power:    unchanged
Relay semantics:                unchanged
ConfigStore durable B:          unchanged
HistoryStore bytes/layout:      unchanged
SecurityStore / BLE / DFU:      unchanged
Role / identity semantics:      unchanged
Geofence operational state:     runtime-only
GNSS runtime scheduling:        intentionally changed only for bounded confirmation
                                and B <-> B/3 re-anchor
```

Location acceptance, geometry, operational state, cadence, persistence, EVENT
transport and LOST/contact remain separate owners.

## Review findings and fixes

Earlier internal review fixed:

1. C++17 nested namespace syntax incompatible with the production gnu++11
   toolchain.
2. Invalid geometry observations during an active episode consuming the wrong
   control path.
3. Accepted representative data being dropped entirely if flash admission
   outlived the 5-second live window.
4. Missing physical test-only probe isolation.

Astra final audit of `bca04b7` returned **PASS WITH FIXES**:
0 BLOCKER, 0 HIGH, 2 MEDIUM, 7 LOW.

The branch now closes the actionable audit findings as follows:

- **MEDIUM — duplicate slot-0 POSITION:** slot 0 is marked as the ordinary
  PositionFlow admission. If it later wins representative selection, it is not
  serialized/stored/transmitted a second time.
- **MEDIUM — composition coverage:** the real host startup harness now includes
  a configured-geofence scenario using actual `setup()/loop()`, normal slot-0
  persistence, bounded confirmation, timeout abort, same-acquisition extra
  fixes, representative de-duplication, B->B/3 re-anchor and +59.999 s no-early
  acquisition check.
- **LOW — deadline race:** coordinator checks the observation capture timestamp;
  an observation captured at/after 10,000 ms cannot complete the episode.
- **LOW — host runner mode:** `firmware/tests/run_host_tests.sh` is restored to
  executable mode.
- **LOW — live ConfigStore B mismatch:** cadence derives from the boot-applied B
  snapshot.
- **LOW — configure/clear ownership trap:** coordinator header now explicitly
  states the composition owner's cancellation/buffer/base-cadence obligations.
- **LOW — indefinitely queued representative:** a pending representative is
  discarded when tracking service is intentionally disabled.
- **LOW — probe diagnostics:** cadence interval/power implication and TTFF
  meaning are explicit.
- **LOW — stale docs:** M6 overview, policy status and this milestone are
  reconciled with M6D2.
