# M3 — Scheduled GNSS acquisition and low-power foundation

> R3 supersedes the historical freshness/UTC and boot-absence details below.
> See [R3 GNSS freshness hardening](../audits/R3_GNSS_FRESHNESS_FIX.md):
> per-callback age, session boundaries, snapshot UTC, bounded detection retry
> and capture-to-live-TX expiry. The wire format and M3 power/schedule policy
> remain unchanged.


## Objective and implementation

Keep one universal RAK4630/RAK4631 firmware codebase and binary while adding
cooperative GNSS acquisition, a configurable fixed schedule, timeout recovery,
GNSS power control, and a supported MCU idle foundation. Firmware version is
defined only in `firmware_version.h`. No profile provisioning was added.

`GnssManager` owns acquisition, volatile receiver configuration, power
transitions, candidate pairing and diagnostics. `RadioManager`, Device ID,
TEST/POSITION codecs and RF settings are unchanged. POSITION remains 34 bytes,
protocol version 1, type 2. No dependencies were added or updated.

## States

| State | Behavior |
| --- | --- |
| `kPowerOff` | Boot: WB_IO2 LOW, cooperatively wait 1 second. |
| `kPowerOnWait` | Boot: WB_IO2 HIGH, cooperatively wait 1 second. |
| `kDetecting` | Start Wire and perform bounded library detection. |
| `kNotPresent` | Detection failed; radio operation continues, no boot retry loop. |
| `kStarting` | Start attempt/timeout clock; settle power on wake, configure one operation per pass, discard pending callbacks. |
| `kAcquiring` | Poll automatic PVT/DOP; accept only a new qualifying matched epoch. |
| `kFixAvailable` | Single-use fix can be handed to radio in the same loop; next pass applies power policy. |
| `kTimeout` | Clear candidates, count timeout, send no position; next pass applies power policy. |
| `kFailure` | Count configuration failure; next pass applies power policy. |
| `kSleeping` | WB_IO2 LOW; no GNSS bus access until next due. |
| `kIdle` | GNSS remains in continuous tracking; drain callbacks without promoting positions until due. |

Boot detection starts the first acquisition immediately, including receiver
configuration. Subsequent wake and volatile configuration are included in the
acquisition timeout and TTFF. Configuration is checked, not assumed successful.
After power-off, timeout or setup failure it is reapplied on the next attempt.
The receiver is configured for UBX, 1 Hz navigation, continuous navigation
mode, and automatic PVT/DOP. No receiver configuration is saved to flash/BBR.

## Configuration and scheduling

Central settings in `firmware/include/gnss_config.h`:

- Tracking interval: **15 minutes (900 seconds)**.
- Acquisition timeout: **120 seconds**, independently configured.
- Short interval threshold: **60 seconds inclusive**.
- Power settling: **1 second** after switching on.
- Minimum useful off gap: **2 seconds**; smaller gaps keep tracking active.
- Unsent fresh-fix lifetime: **5 seconds**, then discard rather than send late.

Settings are compile-time constants ready for later ConfigManager integration;
there is no persistent, BLE or LoRa configuration service in M3. Supported
intervals are positive, up to 12 days (within the monotonic half-range);
10/20/30/60 seconds, 5 minutes and 15 minutes are covered by deterministic
schedule/policy checks. The timeout is separately range-checked at compile time.

The first acquisition start anchors a fixed grid. At each due time, start one
attempt and advance the next due to the first future grid point. Completion,
timeout and failure also skip every grid point reached while busy. No overlapping
acquisitions, queued attempts or catch-up packet bursts occur. Fix acceptance
does not wait for another interval. Radio busy state can defer handoff for at
most the fresh-fix lifetime; no history queue is created.

For example, with a 10-second interval an acquisition finishing at 35 seconds
skips 10/20/30 and next starts at 40 seconds. Timeout at 120 seconds next starts
at 130 seconds. A delayed loop uses division to skip slots in constant time.

## Rollover handling

`monotonic_time.h` uses unsigned subtraction for elapsed time and modular
half-range deadline comparisons. Durations/deadlines and the maximum gap
between schedule observations must be below 2^31 ms (about 24.9 days).
`nextFuture` advances the existing phase and is safe across UINT32_MAX -> 0.

The installed Adafruit nRF52 1.7.0 core has an additional trap: `delay.c`
implements `millis()` as `tick2ms(xTaskGetTickCount())`, with 1024 Hz ticks.
Its raw tick counter wraps after about 48.5 days, so that clock does not wrap
at 2^32 milliseconds. M3 extends unsigned RTOS tick deltas before conversion
to a uint32 millisecond clock. Both the tick wrap and the resulting normal
millisecond wrap are host-tested. This clock is used only from the loop task
and must be sampled at least once per raw tick wrap. It keeps advancing during
RTOS idle. Existing radio/library clocks are unchanged; the disabled M1 test
beacon's legacy scheduler is not covered by the new GNSS clock guarantee.

## Fresh-fix integration

On every attempt, application PVT/DOP candidates and any old unsent fix are
cleared. STARTING drains receiver output and library callbacks with acceptance
disabled. Library parser state, allocations and callback registration are not
manually reset. In library 2.2.29, `flushPVT`/`flushDOP` clear getter flags,
not callback copies, so they are not used as a queue flush.

The first PVT epoch after draining is a boundary and is not transmitted. A
different epoch is required, protecting against buffered/partial old messages;
this conservatively costs a navigation epoch. Epoch comparison uses equality,
including GPS-week rollover. The M2 last-promoted-epoch guard is retained.

Both callback orders work. Acceptance still requires gnssFixOK, navigation fix
type 2/3/4, valid LLH, legal coordinates and identical PVT/DOP iTOW. Invalid
UTC alone does not reject coordinates: epoch remains zero and UTC-valid is
clear. The promoted fix cannot be overwritten or consumed twice. A fix at or
after the timeout is rejected. Timeout/failure never creates POSITION.

## GNSS power strategy and evidence

M3 selects **B: official RAK12500 WB_IO2 switched-power control** for long
intervals. Wake raises WB_IO2, cooperatively settles for 1 second, and reapplies
configuration. Short intervals keep continuous tracking; they do not toggle
power after every report. The same keep-on policy applies after timeout.

Evidence inspected:

- [RAK12500 official I2C example](https://github.com/RAKWireless/WisBlock/blob/master/examples/common/sensors/RAK12500_GPS_ZOE-M8Q/RAK12500_GPS_ZOE-M8Q_IIC/RAK12500_GPS_ZOE-M8Q_IIC.ino)
  uses WB_IO2 LOW/HIGH with one-second waits before Wire/GNSS initialization.
- [RAK tracker GNSS implementation](https://github.com/RAKWireless/LPWAN-Tracker-Solution/blob/main/PlatformIO/src/gnss.cpp)
  uses WB_IO2 HIGH before GNSS initialization and LOW after polling.
  Only its power-control evidence is used; its LoRaWAN/blocking logic is not imported.
- [RAK12500 datasheet and schematic](https://docs.rakwireless.com/product-categories/wisblock/rak12500/datasheet/)
  exposes switched 3V3_S and VDD supplies. The linked schematic marks RTC
  crystal X4 `32.768K/NC`, with its capacitors also NC. Installed assembly
  revision and RTC population cannot be established without hardware.
- [ZOE-M8 data sheet, sections 1.21.2 and 1.22.3](https://content.u-blox.com/sites/default/files/ZOE-M8_DataSheet_UBX-16008094.pdf)
  documents RTC provision, backup supply requirements, and software backup.
  An externally provided RTC supports retained time and some power-save
  operations. Software backup requires supply to remain present.
- [M8 protocol, section 32.18.3](https://content.u-blox.com/sites/default/files/products/documents/u-blox8-M8_ReceiverDescrProtSpec_UBX-13003221.pdf)
  documents timed PMREQ and pin wake sources. I2C is not a specified wake
  source. Timed backup wake on this particular RAK12500 assembly is therefore
  not assumed safe in M3.
- Installed SparkFun **2.2.29** source and `Example22_PowerOff` were inspected:
  `powerOff` builds the 8-byte PMREQ; `powerOffWithInterrupt` builds the 16-byte
  form. With maxWait zero, `powerOff` sends then unconditionally returns false;
  with nonzero maxWait its return is a NACK check, not sleep confirmation.
  `powerSaveMode(false)` uses documented CFG-RXM continuous mode and rejects
  unsupported protocol generations. No custom UBX payload was invented.

WB_IO2 is a shared switched sensor supply, not a private GNSS enable pin.
Future sensor services must coordinate ownership before using this policy
alongside other switched-rail modules. The vendored RAK4630 variant maps it
to nRF52840 P1.02 (34), and provides Wire pins 13/14 and USE_LFXO. Vendor
sources were inspected and left unchanged.

No claim is made that backup RAM, RTC, almanac or ephemeris survive this
power strategy. Long intervals may incur cold starts. The short-interval
policy avoids repeated power cycling when that would be counterproductive.

## MCU idle/sleep strategy

`PowerManager::idle()` retains the existing 10 ms loop service period using
the verified core `delay()` implementation: USB CDC flush followed by
`vTaskDelay`. Adafruit nRF52 1.7.0 enables tickless idle. Its
`vPortSuppressTicksAndSleep` in `port_cmsis_systick.c` handles RTC compare,
SoftDevice-aware event wait and tick correction when tasks are idle.
This is a supported foundation, not a measured power improvement over M2's
existing delay. No SYSTEM OFF, direct WFI/WFE, reset wake or interrupt masking
is added by the application. USB and radio tasks remain enabled.

## Diagnostics

`diagnostics()` exposes runtime uint32 counters for acquisition attempts,
successful accepted fresh fixes, acquisition timeouts, invalid PVT fixes,
configuration failures and expired unsent fixes. Counters are not persistent
and are not inserted into POSITION. `last_ttff_ms` is unsigned monotonic time
from attempt start through power settling/configuration to accepted fresh
PVT/DOP; it remains the last successful value after a timeout. Success counts
fix acceptance, not LoRa delivery. Serial logs occur at transitions/fixes only,
including TTFF, satellites and HDOP; no polling spam was added.

## Physical validation required and limitations

All physical hardware validation remains **pending**:

- Boot detection with and without RAK12500; actual slot/rail behavior.
- First fix, repeated power-off/wake/configuration cycles, warm/hot versus
  cold restart behavior, RTC population and backup retention if any.
- TTFF distribution and timeout recovery with no sky view and restored signal.
- Repeated 15-minute cycles; 10/20/30/60-second continuous-tracking trials.
- LoRa RX/TX before, during and after GNSS wake/sleep, including peer RSSI/SNR.
- Actual current during acquisition and idle, with/without USB; verify USB
  debug connectivity and wake behavior while the scheduler idles.
- No stale or duplicate POSITION after failed acquisition, missing DOP,
  delayed radio availability or receiver reset; invalid UTC coordinates remain usable.

Acquisition has no fix-wait loop or long delay. Library setup still uses
bounded synchronous operations (250 ms per requested wait; `begin` may retry
three times and setters may perform multiple transactions). The installed
Wire driver has peripheral busy waits without an application-configurable
bus timeout; a physically stuck I2C bus is not solved by this milestone.
Boot absence is not hot-plug detection. Maximum idle current, TTFF, successful
wake, battery life and over-the-air operation are not established by builds.

SX1262 continues receiving between transmissions for all nodes. Full tracker
radio duty-cycling/RX windows need future node profile/config support; M3 does
not impose a global radio sleep policy on future BASE/RELAY/MOBILE nodes.
No flash history, ACK/retry, relay, geofence, activity, LOST/SEARCH, BLE config,
authentication, OTA or applications were added.

**M6P1 supersession:** `docs/milestones/M6P1.md` gives the legacy TRACKER role
a bounded post-transmission RX window followed by sleep, superseding "continues
receiving between transmissions for all nodes" for TRACKER only. BASE and
forwarding-enabled RELAY still keep continuous RX exactly as described above.
Separately, `docs/milestones/M6P1.md`'s "GNSS tracking interval" section
supersedes the "Tracking interval: 15 minutes (900 seconds)" bullet above:
`kTrackingIntervalSeconds` is currently `3 * 60` (180 s), an intentional
compile-time development/test default, not a change to the scheduling logic
described in this document.

## M4 prerequisites

Complete the hardware checks above and resolve any power/wake or bus faults.
Establish usable flash capacity/ownership and endurance before implementing a
circular log. Then insert store-before-transmit at the fresh-fix handoff,
prioritize live/critical data over historical backlog, and define delivery
confirmation semantics before retiring stored records. M3 only offers a
single volatile fix buffer; it does not provide store-and-forward guarantees.
