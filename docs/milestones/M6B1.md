# M6B1 — Host-only activity window core

Status: **IN PROGRESS; NOT PRODUCTION-INTEGRATED**.

Stacked baseline: `feat/m6a-accelerometer-foundation@a4e5a9b1ae7f1143c4ec70441a51e0b1c978329d`.
Branch: `feat/m6b-activity-core`.

## Purpose

M6B1 uses the time while M6A physical RAK1904 validation is pending to build only the portable, deterministic activity-processing trunk that does not depend on unproven hardware behavior.

The slice consumes `AccelerometerSample` observations and produces bounded fixed-memory window features. It does **not** read I2C, control RAK1904 power, alter runtime configuration, run from `main.cpp`, transmit RF, write flash, or claim cattle-behavior accuracy.

## Current window seed

Initial host-only policy:

- 10 Hz sample assumption;
- 50 samples / approximately 5 seconds per window;
- no dynamic allocation and no raw-sample window buffer;
- streaming integer accumulators only;
- timing discontinuity recorded when adjacent capture timestamps are equal or more than 300 ms apart;
- millis rollover handled with unsigned elapsed-time arithmetic.

The 5-second window and timing policy are implementation seeds, **not validated animal-classification parameters**. They may change after real collar/animal data without implying a wire/storage compatibility change.

## Features

The current pure feature boundary exposes:

- sample count and window duration;
- timing-continuity status and discontinuity count;
- per-axis mean;
- per-axis population variance and summed axis variance;
- mean squared acceleration magnitude, without square root/floating point;
- mean adjacent-sample Manhattan delta as a lightweight motion/jerk proxy.

Wide accumulators are used so the fixed-point calculations remain defined over the full `int16_t` input domain.

## Deliberate non-goals

M6B1 does not yet implement or claim:

- RESTING / GRAZING / WALKING thresholds;
- a trained model;
- classifier accuracy;
- continuous production sampling;
- FIFO/interrupt policy;
- sensor-to-activity runtime wiring;
- activity persistence/history;
- activity RF payloads/events;
- power-policy changes.

The behavior-class enum/threshold policy should not be frozen from synthetic data. Classification comes after M6A physical sample behavior is known and field/collar evidence exists.

## Compatibility and ownership impact

Expected impact for this host-only slice:

```text
Protocol/TLP v1: unchanged
RF/airtime:       unchanged
Storage/flash:    unchanged
GNSS:             unchanged
RAK1904 driver:   unchanged
main.cpp runtime: unchanged
RequestedConfig:  unchanged
Power ownership:  unchanged
```

`activity_window.*` owns only deterministic local feature accumulation. Accelerometer hardware remains owned by M6A; future activity service integration must not make hardware presence imply service enablement.

## Validation

`firmware/tests/m6/test_m6_activity.cpp` covers:

- empty/incomplete window refusal;
- static 1 g window;
- orientation-independent squared-magnitude feature;
- deterministic dynamic variance/delta values;
- timing gap diagnostics without silent sample loss;
- `millis()` rollover;
- full-range `int16_t` arithmetic/accumulator safety;
- completed-window take/reset ownership.

The test is compiled under `gnu++11` with `-Wall -Wextra -Werror` and ASan/UBSan by the normal host runner so the portable core remains compatible with the current RAK GCC/C++ baseline before production integration.

No physical hardware validation is required for M6B1 itself because this slice is not connected to production sensor/runtime behavior. M6A physical validation remains a separate gate.
