## Purpose

M6P1 gives the animal TRACKER a bounded post-transmission RX window instead of
continuous RX, so a battery-powered collar is not required to keep the SX1262
receiving indefinitely between its own transmissions. BASE, RELAY-enabled and
any role transitioning must keep continuous RX; this slice changes TRACKER
radio duty-cycling only and does not touch GNSS, activity, geofence, storage,
identity or TLP v1 bytes.

## GNSS tracking interval — development default (3 minutes)

`kTrackingIntervalSeconds` in `firmware/include/gnss_config.h` is `3 * 60`
(180 seconds), not the earlier `15 * 60` (900 seconds).

History: the 2026-09-17 physical test session below originally used this
same single-line change as a temporary, uncommitted local override purely to
shorten manual iteration time. On 2026-09-18 the product owner explicitly
adopted that same value as the intentional compile-time development/test
default while ORUN TLP remains in active development — this is now a
deliberate development-default decision, not a leftover test artifact, and
the physical evidence gathered under it (below) is evidence for the current
default, not for a discarded override.

Scope of this change, explicitly:

- Exactly one constant value changed. No runtime/application configuration
  system, BLE command, persistence, or protocol/wire change was added.
  AGENTS.md's long-term goal of runtime-configurable tracking interval
  remains unimplemented future work, not delivered here.
- Effect versus the previous 15-minute default: approximately 5x more
  frequent tracking schedule, more frequent GNSS acquisition, more frequent
  POSITION generation, more frequent RF TX, and more storage records
  written. Higher energy consumption is expected as a consequence, but no
  quantitative power measurement exists for either interval (see §7 below),
  so no battery-life claim is made or implied by this change.
- `kShortIntervalThresholdSeconds` (60 seconds) is unchanged. 180 seconds is
  still above that threshold, so in `firmware/src/gnss_manager.cpp`,
  `GnssManager::enterLowPower()`'s `gnss_config::keepTracking(interval_ms,
  remaining_ms)` gate — `interval_ms <= kShortIntervalThresholdMs ||
  remaining_ms <= kMinimumPowerOffMs` — still evaluates false in the normal
  case, so the existing fix/timeout -> `SensorPowerManager::release(kGnss)`
  (`3V3_S` release) -> next schedule -> reacquire power-cycle behavior is
  preserved in kind at 3 minutes, only more frequent. This was verified
  directly against the current source, not assumed.

## Listen policy

`resolveRadioListenPolicy()` (`radio_listen_policy.h/.cpp`) is a pure function
of already-resolved runtime facts — relay forwarding running, whether the node
receives application POSITION traffic, and whether a role transition is
pending — and returns `kContinuous` or `kWindowed`. It does not know `NodeRole`
names; `legacyRoleBehavior()` in `node_role.h` is the only place that maps the
legacy TRACKER/RELAY/BASE projection onto those facts. Today this yields
`kWindowed` for TRACKER only and `kContinuous` for RELAY (forwarding on) and
BASE (`receive_application_position`).

## State machine

`RadioManager` adds `RadioListenState`: `CONTINUOUS` / `WINDOW` / `ASLEEP`.

```text
kContinuous policy            -> always CONTINUOUS, RX restored whenever needed
kWindowed policy, local TX terminal completion -> opens a new WINDOW,
                                   deadline = now + kWindowedRxAfterTxMs (3000 ms)
WINDOW, RX done/error/timeout  -> RX restore only, inside the already-open window;
                                   does NOT extend or replace the fixed deadline
WINDOW, deadline reached       -> ASLEEP (Radio.Sleep(), RX accounting folded)
ASLEEP, RX restore requested   -> ignored, no window opens; counted in
                                   stale_restores_while_asleep
ASLEEP, local TX needed        -> wakes for TX only, counted in wakes_for_tx
local TX terminal completion (from WINDOW or ASLEEP) -> opens a new WINDOW
```

The window deadline is fixed at the moment a local TX terminates (success or
timeout) and is never extended mid-window. An RX completion, RX error, RX
timeout, or a stale/terminal TX result observed while a window is already open
only restores RX within that same window; it never pushes the deadline out and
never, by itself, opens a window from `ASLEEP`. Only a local TX terminal
completion opens a new window and sets a new deadline. When the deadline is
reached the node returns to `ASLEEP` until its next local TX. A role
transition or relay-forwarding enable always forces continuous RX before the
transition completes.

## Driver evidence (SX126x-Arduino 2.0.32)

Read directly from `.pio/libdeps/rak4630/SX126x-Arduino/src`:

- `RadioSleep()` sets `SleepParams_t.WarmStart = 1` and calls
  `SX126xSetSleep()`, which issues `RADIO_SET_SLEEP` through
  `SX126xWriteCommand()` and only then sets `MODE_SLEEP`.
- `SX126xWriteCommand()` always calls `SX126xCheckDeviceReady()` first; that
  function wakes the radio (`SX126xWakeup()`) whenever the tracked mode is
  `MODE_SLEEP` or `MODE_RX_DC`. Every subsequent driver command — including
  `Radio.Rx()` and `Radio.Send()` — therefore wakes a sleeping SX1262 as a side
  effect of the first register write, before this owner issues anything else.
- `RadioSend()` re-applies `SX126xSetPacketParams()` on every call, so TX
  parameters are reasserted after sleep rather than assumed retained.
- Sync word and modulation-parameter retention across `WarmStart` sleep is a
  library/silicon property this review did not re-derive from source; it is a
  hardware-validation item, not a software claim (see Known limits).

## `RADIO?` diagnostics

```text
RADIO policy=<CONTINUOUS|WINDOWED> state=<CONTINUOUS|WINDOW|ASLEEP>
windows=<N> sleeps=<N> wakes=<N> rx_in_window=<N> stale=<N> rx_ms_est=<N>
```

`rx_ms_est` is `RadioListenDiagnostics.estimated_rx_ms`, a saturating
millisecond accumulator folded on every `update()` pass (`foldRxAccounting()`)
so it stays current even across a very long single RX interval instead of only
updating at RX stop. It saturates at `UINT32_MAX` and does not wrap.

## Review record

This document records a fix applied directly during independent review of
`37feabf`/`a2deba7` before merge, not a separate post-merge audit pass:

1. `processCallbackEvents()` consumed a stale/terminal TX result in its
   `else` branch (`++event_diagnostics_.stale_tx_results`) without restoring
   RX, unlike every other terminal path in that function. Fixed by keeping the
   pre-M6P1 defensive `requestRxRestore()` after the whole `tx_result` block;
   an asleep windowed node ignores and counts the request as before.
2. `RadioListenDiagnostics.estimated_rx_ms` only advanced when RX stopped
   (`markRxStopped`), so a node parked in one very long continuous RX interval
   would under-report elapsed RX time and the counter could jump/overflow
   unevenly. Fixed with `foldRxAccounting(now)`, called once per `update()`
   pass, which folds elapsed time into the saturating accumulator and rebases
   the running start time without touching `rx_accounting_active_`.
3. Formatting-only drift introduced against the `5b18990` baseline style
   (line-wrap/brace-style changes unrelated to M6P1 logic, a redundant
   `#include <string.h>`, and a missing trailing newline) was reverted so the
   diff against baseline contains only meaningful M6P1 changes.

## Known limits

- Sync word/modulation retention across `WarmStart` sleep is asserted from
  driver source reading, not from an oscilloscope/logic-analyzer or packet
  capture on real hardware.
- `estimated_rx_ms` is a software time estimate derived from driver state
  transitions, not a measured radio-on duration.
- The 3000 ms post-TX window was the M6P1 validated setting; it is superseded
  by M6P2's 10000 ms development default. M6P1 physical evidence does not
  validate the newer duration. The TRACKER-only windowed assignment remains
  current, and quantitative power remains unmeasured.
- The 3-minute GNSS tracking interval is an intentional development/test
  default (see "GNSS tracking interval" above), not a validated field
  power-budget parameter and not a battery-life recommendation.
- Quantitative current/power and the RELAY forwarded path were not measured
  or re-run in this closure (§7, §8); FUNCTIONAL HARDWARE PASS above covers
  radio-window state-machine, direct-RF behavior, and GNSS
  acquisition/reacquisition-timing behavior only.

## Follow-up

- Quantitative current measurement (idle/sleep/GNSS/TX-RX duty) requires
  power-measurement instrumentation (e.g. PPK2 or equivalent) not available
  during this closure.
- `TRACKER -> RELAY -> BASE`, `path=RELAY`, should be physically re-run when
  the product owner schedules it; currently deferred, not abandoned.
- A from-clean-boot RELAY/BASE `sleeps=0` acceptance re-run remains open
  (see §3).
- RAK12500 `V_BCKP` electrical behavior across TRACKER sleep/wake cycles is
  still not characterized at the electrical level and should be checked
  before any power-budget claim is made.
- Remaining current-draw suspects (GNSS warm/cold start policy, accelerometer
  idle draw, USB/BLE boot window) remain open from earlier milestones and are
  not resolved by M6P1.
- Before any field/production deployment, revisit the 3-minute development
  default tracking interval and decide a production value together with
  quantitative power measurement; runtime/application configurability of the
  interval (per AGENTS.md) remains unimplemented future work.
