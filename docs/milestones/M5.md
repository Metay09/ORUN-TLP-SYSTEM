# M5 — Direct reception and single-hop relay

## Objective and architecture

M5 extends the one universal RAK4630/RAK4631 binary with TRACKER→BASE direct
reception and TRACKER→RELAY→BASE forwarding. `NodeRole`, `NetworkService`, the
fixed queue/dedupe structures and the RELAY_FORWARD codec are hardware-neutral.
After R2 hardening, the Arduino loop is the single application SX1262 owner;
dependency callbacks only publish bounded events for later owner processing.

M4 is unchanged in meaning: TRACKER fresh fix → persistent commit/readback →
live POSITION TX. A relay does not alter or resequence the original packet.
TX_DONE never marks TRACKER history delivered, and M5 adds no ACK, receipt or
automatic backlog replay.

## Runtime roles

The binary starts in AUTO with BASE as the safe temporary role while GNSS
detection completes. Detected GNSS selects TRACKER; no detected GNSS selects
BASE. Detection itself continues independently of role. Network/service gating
allows only TRACKER to consume fresh fixes into `PositionFlow`; RELAY and BASE
do not produce tracker POSITION traffic. Hardware detection and the universal
code path are retained.

USB Serial provides a bounded, non-blocking, case-insensitive development
override. At most 32 input bytes are serviced per loop and the fixed command
buffer is 24 bytes; no dynamic `String` is used:

```text
ROLE?
ROLE TRACKER
ROLE RELAY
ROLE BASE
```

An override lasts until reboot. It is temporary M5 test provisioning, not the
persistent profile/configuration system planned for M7. Changing role clears
volatile network queues/dedupe and invalidates queued RX events from the prior
role after a driver quiescence barrier. An already active TX finishes or reaches
its owner timeout; owner processing then installs the new radio role and restores
continuous RX. Until then USB reports the requested role. Repeating the installed
role cancels an unapplied transition.

## Relay flow, timing and queue

A RELAY validates a direct 34-byte POSITION, checks the exact
`(source_device_id, sequence_number)` against a 16-entry round-robin RAM cache,
and enqueues unseen traffic. RELAY_FORWARD and TEST are never enqueued. Cache
comparison does not infer numeric sequence ordering, so wrap is harmless.

The forwarding queue contains four fixed entries with exact packet bytes,
ingress metrics and a rollover-safe deadline. It uses no heap. If full, the
newest arrival is dropped while existing scheduled entries keep their
deadlines; a counter and one RX-driven log are produced. The dropped key is not
cached, allowing a later repeat to be accepted after queue space opens.

Delay is an integer in **1200–4200 ms inclusive**, selected by a deterministic
32-bit avalanche hash of original source ID, original sequence and relay ID.
The same tuple always produces the same result, different relays distribute
over the window, and no random seed is required. Unsigned modular deadline
comparison and deadline creation use the existing M3 safe monotonic clock.
This avoids the Adafruit core's earlier raw tick rollover while retaining
normal uint32 millisecond wrap handling.
The 3001-value window is deliberately modest rather than a MAC/TDMA scheme.

Only `RadioManager::update` starts a due forward and only when no other TX is
active. The queue cannot start another forward until owner processing of
TX_DONE/TX_TIMEOUT clears the active radio state. Callbacks do not start radio
operations; the owner restores continuous RX after the dependency callback and
cleanup boundary protected by a static driver mutex. R2.1 pins a reproducible
dependency patch and moves the software TX deadline to the owner monotonic
clock; see [the R2/R2.1 audit](../audits/R2_RADIO_CONCURRENCY_FIX.md).
TX timeout is a local failure diagnostic, not evidence about BASE receipt.

## Envelope and BASE semantics

RELAY_FORWARD is version 1/type `0x03`, exactly 49 bytes: 15-byte envelope
header plus the exact 34-byte original POSITION. It carries relay ID, hop count
one, original length, TRACKER→RELAY RSSI/SNR and original bytes. Full offsets,
signedness and validation are in
[M5_RELAY_FORWARD_PACKET.md](../../protocol/M5_RELAY_FORWARD_PACKET.md).

BASE validates direct POSITION and relay envelope/inner POSITION independently.
Its 32-entry round-robin RAM dedupe cache accepts the first observation as one
new application datum. A later direct or relay copy is a duplicate datum, but
still increments/logs its path observation with RF metrics. The same rule works
in either arrival order. Direct observations carry TRACKER→BASE metrics.
Relayed observations retain TRACKER→RELAY metrics from the envelope and add
RELAY→BASE metrics from the BASE callback. No metrics are normalized.

TRACKER never forwards. RELAY rejects every type `0x03`, and the decoder also
rejects hop count other than one and nested inner type `0x03`. Multi-hop and
relay-of-relay therefore have no transmission path.

## Airtime engineering estimate

For the unchanged test profile—869.525 MHz, SF11, BW125, CR4/5, preamble 8,
explicit header, PHY CRC and low-data-rate optimization—the same formula used
by SX126x-Arduino `RadioTimeOnAir` gives:

- 34-byte POSITION: **987.136 ms** (library integer result approximately 988 ms).
- 49-byte RELAY_FORWARD: **1232.896 ms** (library integer result approximately
  1233 ms).

These are formula estimates, not RF measurements. The 1200–4200 ms relay delay
is comparable to one relay-envelope airtime at its lower bound and spreads
parallel relays over another 3 seconds. It is not claimed collision-optimal.
The configured frequency and 14 dBm conducted power are unchanged. Applicable
frequency, antenna ERP, airtime and duty-cycle/legal compliance must be checked
for the final jurisdiction and deployment pattern.

## Diagnostics and logs

RELAY RAM counters cover valid direct packets, duplicates suppressed, queued,
queue drops, forward attempts/completions/failures, malformed packets and
nested/relayed rejections. BASE counters cover new application data,
duplicates, direct observations, relay observations and malformed envelopes.
Existing radio TX attempts/timeouts remain. Counters are not persisted and do
not change POSITION or storage formats.

Logs occur on RX, queue, duplicate/drop, TX or callback events, never every
poll. BASE NEW/DUP logs retain path and both available link metrics.

## Physical validation and known limitations

Hardware is unavailable, so the following remain pending: three RAK devices
running the same binary; all runtime roles; direct TRACKER→BASE; both relay
links; both direct/relay arrival orders and loss cases; repeated packets,
queue pressure and relay RX restoration; on-air envelope bytes; RSSI/SNR units;
actual airtime/collisions; hill/terrain range; flash/GNSS/radio interaction;
and power behavior in each role.

The role is volatile, caches reset on boot, one queue drop has no RF retry,
dedupe is bounded RAM, and no authentication prevents forged envelopes. M5 has
one hop only and no receipt confirmation. M6 may consume BASE's one-time
application event but must not reinterpret it as TRACKER journal delivery;
physical M5 radio validation and future persistent profile design remain
prerequisites for deployment.
