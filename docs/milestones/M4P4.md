# M4P4 — SF2 secure historical observation + BACKEND_DURABLE receipt codec

Status: **INDEPENDENT AUDIT PASS WITH FIXES; FIXES APPLIED; REVALIDATION PENDING — NOT YET FROZEN OR RUNTIME-ACTIVE.**

Baseline:
`main@38536fdd324d5fc1fd7762068ef21cdd842b1885`
(M4P3 merged via PR #71).

Branch:
`feat/m4p4-store-forward-secure-codec`.

## 1. Purpose

M4P3 physically closed the History v4 observation-stream incarnation required
by the store-forward identity contract.

M4P4 is SF2. It freezes no replay runtime yet. It defines and validates the
smallest exact secure wire needed for:

1. device -> backend historical POSITION observation;
2. backend -> device authenticated `BACKEND_DURABLE` receipt.

The product invariant remains:

```text
logical observation =
(DeviceIdentity, HistoryIncarnation, HistoryRecordIdentity)
```

A gateway/relay may transport these bytes but must not possess authority to mint
a `BACKEND_DURABLE` receipt.

## 2. Security boundary reused, not reinvented

This candidate reuses the independently reviewed M7P6D/M7P6E root-credential
traffic-direction contract:

```text
KDF/nonce direction_u8:
D2A = 0x01
A2D = 0x02

K_traffic =
HKDF-Expand(
  HKDF-Extract(SHA-256, credential_id, K_root),
  ASCII("ORUN-TLP-V2-AEAD") || direction_u8 || key_epoch_be32,
  16)

nonce =
key_epoch_be32 || direction_u8 || security_counter_be64
```

These traffic direction bytes are **not** the on-air
`security_context` registry. Canonical TLP v2 header contexts remain:

```text
0x01 BACKEND_A2D
0x02 DEVICE_D2A
0x03 DELEGATED_GW2D
0x04 DELEGATED_D2GW
```

M4P4 therefore uses an explicit fixed mapping:

```text
header DEVICE_D2A 0x02 -> KDF/nonce D2A direction 0x01
header BACKEND_A2D 0x01 -> KDF/nonce A2D direction 0x02
```

The two namespaces must never be inferred by numeric equality.

AES-128-CCM with an 8-byte tag remains the reviewed/pinned candidate.

This slice does not add production crypto execution. It adds a bounded codec and
wire fixtures only.

It deliberately does **not** reuse `DELEGATED_SECURE_APP`. Delegated gateway
material must never authorize History delivery advancement.

## 3. Exact candidate secure envelope

All integers are big-endian.

```text
off size field
0   1    version = 0x02
1   1    type = 0x03 HISTORY_SECURE
2   1    security_context
3   1    app_family
4   1    path_flags
5   1    ciphertext_len
6   2    reserved = 0
8   8    device_id
16  4    key_epoch
20  8    security_counter
28  8    history_incarnation
36  N    ciphertext
36+N 8   AES-CCM tag
```

AAD is exactly bytes `0..35`.

`device_id` semantics are direction-owned:

- DEVICE_D2A observation: authenticated source device;
- BACKEND_A2D receipt: authenticated target device.

After AEAD success, the security owner must verify the header device binding
against the resolved credential lifetime. No unauthenticated identity claim is
authority.

`history_incarnation` is always authenticated AAD and must be nonzero.

## 4. Context/family matrix

```text
0x02 DEVICE_D2A
  -> 0x01 HISTORY_POSITION_OBSERVATION

0x01 BACKEND_A2D
  -> 0x02 BACKEND_DURABLE_RECEIPT
```

Every other combination rejects structurally.

`path_flags bit0 = relay_allowed`. Other bits reject.

TLP v2 type `0x02` remains reserved by the already-reviewed candidate secure
relay-wrapper direction. M4P4 allocates `0x03` only inside TLP v2; TLP v1 type
values remain untouched.

## 5. Historical POSITION plaintext

Exact plaintext size: **29 bytes**.

```text
off size field
0   1    schema = 1
1   8    history_record_identity
9   4    gnss_utc_epoch_seconds
13  4    latitude_e7
17  4    longitude_e7
21  4    altitude_mm
25  2    hdop_x100
27  1    satellites
28  1    position_flags
```

The source device and History incarnation are not duplicated in ciphertext;
they are authenticated by the secure header.

The legacy uint32 POSITION sequence is not duplicated either. Current History
format v4 already requires:

```text
position.sequence_number == uint32(history_record_identity - 1)
```

so the backend can derive that compatibility field when needed without making
the uint32 sequence the logical observation identity.

Historical/replay meaning is unambiguous from the exact packet family. This is
not a blind replay of TLP v1 POSITION bytes.

Time semantics preserve the existing stored-record contract:

- `VALID_UTC_TIME` set -> UTC field is presented as valid-time provenance;
- `VALID_UTC_TIME` clear -> UTC must be zero and time quality is UNKNOWN.

The current valid-fix requirement is retained. Latitude and longitude validity
matches the existing TLP v1 / History invariant exactly:

```text
-90.0000000 <= latitude <= +90.0000000
-180.0000000 <= longitude <= +180.0000000
```

Out-of-range coordinates reject on both serialize and deserialize.

For UNKNOWN observation time, backend/application code must preserve
`time_quality=UNKNOWN`. Gateway/backend receipt or ingestion time may be stored
as separate path/ingestion metadata but must never be substituted for
observation time.

Total protected observation frame:

```text
36 header + 29 ciphertext + 8 tag = 73 bytes
```

## 6. BACKEND_DURABLE receipt plaintext

Receipt carries explicit identities, never a numeric cumulative range.

```text
off size field
0   1    schema = 1
1   1    scope = 1 BACKEND_DURABLE
2   1    count = 1..6
3   1    reserved = 0
4   8*N  explicit history_record_identity values
```

Rules:

- all identities belong to the header's exact device + History incarnation;
- IDs are nonzero;
- IDs are strictly increasing, providing one canonical encoding and rejecting
  duplicates;
- max batch is **6 explicit IDs**;
- no `delivered-through N`, range, bitmap or implicit gap acknowledgement
  exists.

Receipt sizes:

```text
1 ID: 36 + 12 + 8 = 56 bytes
6 ID: 36 + 52 + 8 = 96 bytes
```

The backend may return fewer than six IDs. Six is a maximum, not a requirement
to delay receipts until a batch is full.

## 7. Airtime feasibility gate

Reference calculation uses the existing engineering RF profile:

- SF11;
- BW 125 kHz;
- CR 4/5;
- preamble 8;
- explicit header;
- CRC enabled.

Calculated raw airtime:

| frame | bytes | airtime |
| --- | ---: | ---: |
| historical observation | 73 | ~1.724416 s |
| 1-ID receipt | 56 | ~1.396736 s |
| 6-ID receipt | 96 | ~2.134016 s |
| relay-wrapped observation candidate | 89 | ~1.970176 s |
| relay-wrapped 1-ID receipt candidate | 72 | ~1.642496 s |
| relay-wrapped 6-ID receipt candidate | 112 | ~2.379776 s |

These are calculations, not RF measurements.

### Stop-and-wait vs bounded batch

Direct one-record stop-and-wait raw airtime:

```text
1.724416 + 1.396736 = 3.121152 s / record
```

Direct six-record batch amortization:

```text
(6 * 1.724416 + 2.134016) / 6
= ~2.080085 s / record
```

One-relay stop-and-wait raw collision-domain airtime:

```text
tracker observation       1.724416
relay wrapped observation 1.970176
gateway receipt           1.396736
relay wrapped receipt     1.642496
----------------------------------
total                     6.733824 s / record
```

One-relay six-record batch amortization:

```text
(6 * (1.724416 + 1.970176) + 2.134016 + 2.379776) / 6
= ~4.446891 s / record
```

The existing contract records that the **current v1** worst-case relayed uplink
may reach a gateway about **5.433 s after TRACKER TX completion**. That timing
includes the current 49-byte relay-forward airtime (~1.232896 s). The candidate
89-byte wrapped historical observation is ~1.970176 s, an additional
~0.737280 s if the existing relay scheduling/turnaround is otherwise unchanged.

Therefore the candidate historical uplink is conservatively modeled at about:

```text
5.433 + 0.737280 = 6.170280 s
```

after TRACKER TX completion before backend processing/Internet latency.

A 1-ID relayed return then needs another:

```text
1.396736 + 1.642496 = 3.039232 s
```

of raw RF airtime. That leaves only about **0.79 s** of the current 10-second
post-TX RX window before any backend processing, Internet latency, relay
turnaround or scheduling jitter.

A max-size six-ID relayed receipt return needs about **4.513792 s** raw airtime,
which already pushes the candidate path past the 10-second window even with
zero backend latency.

This is an engineering extrapolation from the current measured/development
timing plus calculated candidate airtime, not a physical measurement of the new
wire. Same-window relayed receipt delivery therefore cannot be a correctness
dependency.

Therefore SF2 must not freeze per-record stop-and-wait as the only progress
mechanism. Explicit-ID batch receipt is required so valid receipts can arrive in
later RX opportunities without preventing bounded additional backlog work.

## 8. Drain-rate model point

M4P4 does **not** freeze SF3 scheduling, but the wire must admit at least one
plausible drain policy whose service rate exceeds record production.

For the current aggressive **development** tracking interval of 180 s:

```text
record production = 20 records/hour
candidate replay attempt cadence 120 s = 30 attempts/hour
nominal attempt-rate ratio = 1.5x production
```

This is not a 1.5x guaranteed drain margin. If every current live observation
remains undelivered and joins backlog, effective historical success must exceed:

```text
20 / 30 = 66.7%
```

merely to stop backlog growth. Put differently, the simple example tolerates
less than ~33.3% **combined effective historical failure** before net drain
falls to zero; retries, receipt loss, collisions and scheduling misses all
consume that budget. A real SF3 policy needs margin above that threshold.

At perfect historical success, if all new live observations also join backlog:

```text
net drain = 30 - 20 = 10 records/hour
728-record full backlog clear time ~= 72.8 h
```

If current live observations are independently accepted by the backend and
their explicit receipts enter the same RAM selective-delivery set, those new
records need not accumulate as backlog. Then the historical service side can
approach 30 records/hour and a 728-record backlog takes about 24.3 h at perfect
success. SF3 must measure/declare which case applies; M4P4 does not assume the
optimistic case.

At a 120-second replay cadence, six-ID batching amortizes raw collision-domain
airtime to approximately:

```text
direct:    2.080085 / 120 = 1.73% per actively draining tracker
one relay: 4.446891 / 120 = 3.71% per actively draining tracker
```

Gateway half-duplex is explicit in this model: the gateway cannot receive the
historical uplink and transmit its receipt simultaneously, so receive,
backend/Internet wait and return downlink are serialized. Backend latency does
not add RF airtime, but it can move the receipt into a later tracker RX
opportunity and therefore increase retry/duplicate cost.

The 180-second interval is **not** a 30-50-device collision-domain feasibility
claim. Even live v1 POSITION alone contributes approximately:

```text
30 devices  @ 180 s -> 16.45% offered raw airtime
50 devices  @ 180 s -> 27.42%
100 devices @ 180 s -> 54.84%
```

before relay amplification, receipts, retries or backlog replay. In an
unslotted ALOHA-like collision domain this is already around or beyond a useful
operating region. Therefore the 180-second case demonstrates only that one
admitted tracker can have a positive service-rate candidate; it does **not**
demonstrate 30-50-device site capacity.

For the current nominal 30-50 active-device product direction, practical
collision-domain feasibility requires substantially longer normal tracking
intervals (for example >=15 minutes under the present SF11 profile), RF-domain
partitioning/scheduling, or another separately reviewed capacity change. At
15 minutes, live v1 POSITION raw offered airtime is approximately 3.29% /
5.48% / 10.97% for 30 / 50 / 100 devices respectively before amplification.

SF3 must therefore:
- admit only a bounded subset of backlog senders at once;
- yield to live/critical traffic;
- include measured loss/retry and backend-latency distributions;
- serialize gateway half-duplex work;
- avoid making same-window receipt arrival a correctness dependency.

History capacity remains 728 records:

```text
180 s interval  -> ~36.4 h
15 min interval -> ~7.58 d
30 min interval -> ~15.17 d
```

This does not claim arbitrary Internet-outage retention.

## 9. Relay boundary

M4P4 does not implement the v2 relay wrapper.

The previously reviewed relay-wrapper candidate adds 16 bytes. Its initial
delegated-command allow-list accepted only `DELEGATED_SECURE_APP`; SF3 or a
separate reviewed relay slice must explicitly add `HISTORY_SECURE` before any
relay forwards this new type.

No existing TLP v1 relay behavior is changed.

## 10. Runtime boundary

M4P4 codec code has no production caller.

This slice does not:

- send historical records over RF;
- decrypt/authenticate RF;
- call SecurityStore A2D replay admission;
- advance History delivery state;
- change the 10-second tracker listen window;
- change relay forwarding;
- add gateway/backend runtime;
- change TLP v1 bytes;
- change History/Config/Security flash layouts;
- change GNSS/BLE/power behavior.

The pre-audit candidate incorrectly reused M7P6D KDF/nonce direction values as
on-air `security_context` codes.

The canonical header registry is now preserved:

```text
0x01 BACKEND_A2D
0x02 DEVICE_D2A
0x03 DELEGATED_GW2D
0x04 DELEGATED_D2GW
```

while M7P6D KDF/nonce directions remain:

```text
0x01 D2A
0x02 A2D
```

A dedicated codec mapping makes this distinction explicit. Observation/receipt
AAD fixtures and CCM tags were regenerated; KDF keys, nonce direction bytes and
ciphertexts are otherwise unchanged.

### M1 — History coordinate validity mismatch — FIXED

M4P4 now enforces the same latitude/longitude ranges as TLP v1/History on both
serialize and deserialize, with boundary and out-of-range negative tests.

### M2 — drain feasibility limitations incomplete — FIXED IN DOCUMENTATION

The model now records:
- combined effective success threshold for the 180 s / 120 s example;
- full-backlog drain time in optimistic and pessimistic live-receipt cases;
- gateway half-duplex serialization and backend-latency impact;

- explicit statement that 180 s is a per-tracker development example, not a
  30-50-device collision-domain capacity claim;

- L4: SF3 requirements explicitly retain A2D HWM/fresh-counter reissue and
