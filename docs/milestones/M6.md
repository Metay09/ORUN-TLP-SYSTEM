## Objective

M6 adds the first local application services above the proven tracking, radio and
storage foundations:

- RAK1904 / LIS3DH accelerometer capability and bounded sample foundation;
- lightweight animal-activity feature processing;
- local polygon geofence primitives and permitted-area composition;
- later local operational-state policy.

M6 must preserve the existing GNSS -> store-before-send -> frozen TLP v1 POSITION
path and the one-hop M5 network behavior. M6 does **not** authorize BLE, durable
general configuration, a new packet family, multi-hop, backend/mobile, remote
commands, messaging or a new security envelope.

## Hard boundary: local state versus trusted LOST/contact

Local activity and local geofence may proceed using accepted fresh local sensor
and location observations.

The following must **not** be claimed until an authenticated receipt/contact
semantic exists:

```text
OUTSIDE + no network contact for N hours -> trustworthy LOST
```

`TX_DONE` is local radio completion only. It is not delivery, receiver custody or
network contact evidence. Local INSIDE / NEAR_FENCE / OUTSIDE state may exist
before trustworthy remote-contact LOST semantics.

## M6A — accelerometer foundation

Original branch evidence root:
`feat/m6a-accelerometer-foundation@a4e5a9b1ae7f1143c4ec70441a51e0b1c978329d`.
Detailed initial review: `docs/audits/PRE_M6A_BRANCH_REVIEW.md`.
Independent-stack audit resolution: `docs/audits/PRE_M6_STACK_AUDIT_RESOLUTION.md`.

### Current implementation

M6A adds the owned RAK1904 / LIS3DH hardware seam with:

- bounded boot detection and explicit UNKNOWN / PRESENT / ABSENT capability
  semantics;
- LIS3DH `WHO_AM_I=0x33` identity confirmation instead of address-only presence;
- fixed-unit `AccelerometerSample` output for later activity logic;
- existing R4 bounded Wire/recovery ownership;
- cooperative one-register/read operation per loop pass;
- no raw XYZ radio transmission;
- no flash allocation or durable activity state.

RAK1904 uses WisBlock VDD rather than the GNSS-switched `3V3_S` rail, so M6A does
**not** acquire/release `SensorPowerManager` / `WB_IO2`. LIS3DH low power is owned
through `CTRL_REG1=0`.

### Earlier M6A review corrections

Two earlier software-review findings were corrected before the independent stack
audit:

1. **M6A-R1 — retained output freshness:** power-down first, configuration while
   stopped, 10 Hz enable last, first ready XYZ set discarded, later ODR sample
   exposed.
2. **M6A-R2 — immediate shutdown recovery:** final `CTRL_REG1=0` is attempted up
   to three times cooperatively; a transient failure may recover and the captured
   sample is never published unless shutdown is confirmed.

### Independent Astra P2 findings and fixes

The independent audit of `8273e243...` found no P0/P1 issue but identified three
M6A P2 defects:

1. **M6A-01 — HR turn-on time:** the previous flow could accept a sample roughly
   two ODR periods after enable even though LIS3DH high-resolution output requires
   `7/ODR` turn-on time. The corrected flow now waits a rollover-safe seven ODR
   periods (700 ms at 10 Hz) before it may inspect DRDY/output, then still discards
   the first ready set and waits a later ODR sample for acceptance.
2. **M6A-02 — cleanup ownership after retry exhaustion:** three failed shutdown
   attempts previously ended in a terminal state and could leave the always-
   powered sensor at 10 Hz if the bus later recovered. The manager now reports
   PRESENT + FAULT and suppresses the sample immediately, while retaining sparse
   cooperative shutdown ownership with a 60-second retry interval until a later
   `CTRL_REG1=0` succeeds. Health does not silently return to OK.
3. **M6A-03 — retained autonomous activity state:** nonzero `ACT_THS` from a
   previous MCU/image session could survive. Configuration now explicitly clears
   `ACT_THS` while powered down; `CTRL_REG1=0` remains first and 10 Hz enable
   remains last.

These are narrow accelerometer sample/power-state fixes. They do not alter role,
tracking, GNSS power, RF, TLP v1, storage, identity or sequence ownership.

## M6B1 — fixed-memory activity feature core

Software-validated branch closure:
`feat/m6b-activity-core@8353e18785cd16d62c43f0c0d5f63418c96a3d0f`.

Current host-only seed:

- approximately 10 Hz assumption;
- 50 samples / approximately 5 seconds;
- fixed-memory streaming accumulators, no raw-sample buffer and no allocation;
- timing sanity band 50..300 ms per adjacent sample;
- mean XYZ, per-axis variance, summed variance, mean squared magnitude and mean
  adjacent-sample Manhattan delta;
- rollover-safe timing;
- full `int16_t` input arithmetic covered with wide accumulators.

The timing/window values are implementation seeds, not validated cattle behavior
parameters. M6B1 is not called by `main.cpp`, does not touch I2C/RF/storage/power,
and does not define RESTING/GRAZING/WALKING thresholds.

Independent Astra review found no arithmetic/UB defect in the M6B1 bounds.

## M6B2 — activity feature eligibility boundary

Software-validated branch closure:
`feat/m6b2-activity-quality@5400977c971cf118c65a134515fc75d4b8dec00e`.

A feature window is classifier-eligible only when its structural facts agree:

```text
complete == true
sample_count == 50
timing_continuous == true
timing_discontinuities == 0
2450 ms <= duration_ms <= 14700 ms
```

The aggregate duration limits are derived from 49 adjacent intervals and the
same M6B1 timing sanity band. Motion/variance/magnitude values do not participate
in eligibility; this is a data-quality gate, not a behavior classifier.

Independent Astra review found no M6B2 correctness defect; extractor-to-quality
integration remains future runtime work.

## M6C1 — local polygon geometry

Original software-validated closure:
`feat/m6c1-geofence-geometry@853622c4849658ec215ae698364c577c1133614b`.

M6C1 provides deterministic integer-only geometry for already-provided E7
coordinates:

- 3..64 effective vertices;
- clockwise/counter-clockwise and concave polygons;
- implicit closing edge or explicit final vertex equal to the first;
- explicit INSIDE / BOUNDARY / OUTSIDE relation;
- invalid coordinate, degenerate and self-intersecting polygon rejection;
- bounded 10-degree latitude/longitude polygon span to keep signed-64-bit
  orientation/translated shoelace arithmetic defined;
- no dynamic allocation.

### Independent Astra M6C-01 correction

The initial local planar domain accepted exact global coordinate singularities:
`latitude = +/-90` and `longitude = +/-180`. At those locations equivalent
physical points may have multiple coordinate representations, so a planar
classifier could return inconsistent results.

M6C remains deliberately local rather than growing a speculative spherical
geometry layer. The current contract therefore fails closed:

```text
exact latitude  -90 / +90   -> unsupported / invalid
exact longitude -180 / +180 -> unsupported / invalid
coordinates immediately inside those limits -> allowed subject to existing rules
```

Invalid singular query points return `kInvalidPoint`, not `kOutside`. Normal
antimeridian-spanning/global polygons remain unsupported.

Owner post-fix validation includes:

- `M6C bounded geofence polygon geometry checks: PASS`;
- `M6C unsupported global-domain rejection checks: PASS`;
- full host regression: **PASS**;
- RAK4630 build: **SUCCESS**.

Independent Astra re-audit closed `M6C-01`, confirmed the 10-degree arithmetic
bound is unchanged, and verified that M6C2 propagates the stricter invalid-domain

M6C1 remains host-only and does not own GNSS freshness, location-source

## M6C2 — multiple permitted area composition

Software-validated branch closure:
`feat/m6c2-geofence-area-set@4858db8e19318ba7cf007fd94d2765b3f9084c0b`.

M6C2 composes valid polygons as a permitted union:

```text
inside any area                           -> INSIDE
otherwise on one or more boundaries       -> BOUNDARY
otherwise                                 -> OUTSIDE
any malformed configured polygon          -> INVALID AREA SET (fail closed)
```

`INSIDE` outranks `BOUNDARY`, independent of polygon order. A malformed later
polygon invalidates the entire set before containment is accepted. M6C2 inherits
M6C1's corrected fail-closed coordinate domain.

M6C2 deliberately does not freeze an arbitrary product limit on permitted-area
count. Before runtime/untrusted configuration integration, the authoritative
configuration owner must impose a bounded area count together with RAM/CPU and
future storage budgets.

## Ownership and invariants

M6 keeps these owners separate:

```text
accelerometer driver/manager -> hardware identity, detection, sample acquisition
capability snapshot           -> support/presence/health observation
activity window               -> deterministic feature accumulation
activity quality              -> classifier eligibility only
location/tracking             -> accepted fresh position
geofence geometry             -> polygon validity + point relation
geofence area-set             -> union semantics across provided polygons
future geofence service       -> quality/near/outside/hysteresis/FREE_GRAZE policy
network/radio                 -> forwarding and transport ownership
persistence                   -> existing explicitly owned regions only
```

M6 must not create any of these implications:

```text
NodeRole => accelerometer present
accelerometer present => activity enabled
activity enabled => relay disabled
GNSS present => geofence enabled
GNSS Power => tracking/geofence service state
TX_DONE => network contact
OUTSIDE => LOST
```
