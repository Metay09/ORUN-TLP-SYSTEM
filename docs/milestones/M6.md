# M6 — Activity, local geofence and operational state

Status: **IN PROGRESS**.
Baseline: `main@859ca4af0abf9f533a54227b38d2b1a5ddcfcccb` after the reviewed B2/B3/B4 merge.

## Objective

M6 adds the first local application services that sit above the proven tracking,
radio and storage foundations:

- RAK1904 / LIS3DH accelerometer support;
- lightweight animal-activity processing;
- local polygon geofence evaluation;
- local operational state needed by those services.

M6 must preserve the existing GNSS -> store-before-send -> frozen TLP v1 POSITION
path and the one-hop M5 network behavior. M6 is not authorization for BLE,
durable general configuration, a new packet family, multi-hop, backend/mobile,
remote commands, messaging or a new security envelope.

## Hard boundary: local state versus trusted LOST/contact

Local activity and local geofence may proceed using accepted fresh location and
local sensor observations.

The following must **not** be claimed in M6 until an authenticated receipt/contact
semantic exists:

```text
OUTSIDE + no network contact for N hours -> trustworthy LOST
```

`TX_DONE` is local radio completion only. It is not delivery, receiver custody or
network contact evidence. M6 may define local INSIDE / NEAR_FENCE / OUTSIDE
state, but trusted network-contact-based LOST remains security/protocol gated.

## Staged implementation

M6 is intentionally split into small reviewable slices so accelerometer, activity,
geofence and later event transport do not become one coupled state machine.

### M6A — accelerometer foundation

Current branch: `feat/m6a-accelerometer-foundation`.

Scope:

- add the owned RAK1904 / LIS3DH hardware seam;
- bounded boot detection with explicit UNKNOWN / PRESENT / ABSENT semantics;
- expose a small fixed-unit accelerometer observation for later activity logic;
- use the existing patched/bounded I2C path and recovery ownership;
- establish approximately 10 Hz as the initial activity sampling target without
  transmitting raw XYZ over LoRa;
- extend capability reporting only as required for the real accelerometer;
- add host coverage and a focused physical RAK1904 detection/sample check.

Non-goals:

- no cattle behavior classifier yet;
- no activity history persistence;
- no activity RF payload;
- no FIFO/interrupt architecture unless the first real implementation needs it;
- no geofence or LOST behavior;
- no generic sensor registry or second-board HAL.

The RAK1904 is an ST LIS3DH I2C module. RAK's current documentation and example
use I2C address `0x18` and the SparkFun LIS3DH library. The project will pin any
new dependency explicitly and measure final flash/RAM cost before accepting it.
The LIS3DH operating mode/sample format must be derived from the ST datasheet,
not copied blindly from an example. Current M6A work must not assume that the
accelerometer shares GNSS's WB_IO2/3V3_S power ownership unless the board wiring
is explicitly proven.

### M6B — activity window and classification

After M6A hardware/sample behavior is proven:

- bounded fixed-memory sample/window processing;
- lightweight features suitable for low-power operation;
- initial classes: stationary/resting, grazing, walking;
- explicit unknown/insufficient-data state;
- no raw XYZ radio stream;
- no claim of animal-behavior accuracy until collar mounting and real animal
  validation are performed.

Research-derived thresholds/models may seed the implementation, but field data is
the validation authority.

### M6C — local geofence engine

Geofence is a local application service and consumes accepted fresh position,
not radio role or GNSS-driver internals.

Initial scope:

- one or more permitted polygons;
- INSIDE / NEAR_FENCE / OUTSIDE;
- explicit point validity/freshness requirements;
- GNSS quality filtering;
- hysteresis and repeated-valid-fix policy where needed to suppress false alarms;
- local FREE_GRAZE semantics, including optional timed suppression of normal
  violation state.

M6C does not alter the 34-byte TLP v1 POSITION packet and does not introduce a
critical EVENT/ACK protocol by itself.

### M6D — local operational state integration

Only after activity and geofence primitives are stable:

- compose local activity/geofence state without coupling it to NodeRole;
- preserve independent tracking and relay-forwarding service behavior;
- define bounded diagnostics and transitions;
- keep trustworthy remote-contact LOST and critical event delivery gated on the
  later reviewed protocol/security work.

## Ownership and invariants

M6 must keep these owners separate:

```text
accelerometer driver/manager -> sensor detection and samples
activity service             -> features/classification
location/tracking             -> accepted fresh position
geofence service              -> polygon/state evaluation
network/radio                 -> forwarding and transport ownership
persistence                   -> existing explicitly owned regions only
```

M6 must not make any of these implications:

```text
NodeRole => accelerometer present
accelerometer present => activity enabled
activity enabled => relay disabled
GNSS present => geofence enabled
TX_DONE => network contact
OUTSIDE => LOST
```

## Compatibility impact expected for M6A

M6A is expected to change no:

- TLP v1 bytes or packet sizes;
- POSITION/RELAY_FORWARD encoding;
- RF frequency, SF, bandwidth, coding rate or TX power;
- M5 one-hop/nested-relay policy;
- history journal format or flash region ownership;
- device identity or sequence semantics;
- GNSS acquisition/freshness state machine;
- GNSS power ownership;
- USB ROLE syntax or AUTO bootstrap behavior.

Any deviation requires an explicit review before merge.

## Validation plan

Normal M6A validation order:

1. focused host tests for detection/sample/capability semantics;
2. complete `./firmware/tests/run_host_tests.sh` regression;
3. warnings/sanitizers through the host suite;
4. `pio run -e rak4630` and RAM/flash comparison against the B4 baseline;
5. one focused physical RAK1904 check on the owned RAK4631 hardware;
6. independent audit before merge if runtime/I2C/power ownership changes are
   non-trivial.

A build PASS is not a RAK1904 hardware PASS. A host sample model is not a cattle
activity-accuracy PASS.
