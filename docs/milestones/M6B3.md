## Scope and ownership

M6B3 is runtime-integrated only as an explicit bounded diagnostic capture seam:

```text
ACTIVITY START -> AccelerometerManager runtime session
              -> 50 AccelerometerSample observations
              -> ActivityWindow -> assessActivityWindow()
              -> confirmed CTRL1=0 shutdown -> latched READY / INVALID
```

`AccelerometerManager` remains the only LIS3DH register/I2C owner. A session can
start only after the complete healthy PRESENT boot probe, with no active session.
It reuses the existing cooperative configuration and cleanup states: CTRL1=0
first, retained-state clearing, CTRL4 BDU/HR +/-2 g, 10 Hz enable last, 700 ms HR
settling, discard the first retained ready sample, then accept later observations.
One bounded sensor operation is performed per poll pass; deadlines are rollover-safe.
The runtime sample is separate from the boot probe sample.

The handoff holds at most one unread sample and never overwrites it. Backpressure
performs no additional sample reads; an unread sample abandoned for 500 ms fails
closed and initiates cleanup. Normal no-data acquisition uses the existing 500 ms
sample timeout. Status and axis reads occur in separate cooperative passes, so
actual intervals can be slightly longer than 100 ms at the existing loop cadence.
This is approximately five seconds of observations plus configuration/settling
and shutdown, not a strict five-second command latency guarantee.

`ActivityCapture` owns one fixed-memory window and the latched feature/assessment
object. After exactly 50 observations it requests stop. Neither READY nor INVALID
nor a feature result is exposed until the manager confirms shutdown. Timing-invalid
windows retain inspectable features but are unusable. Sensor/configuration/sample
faults suppress the result and preserve PRESENT + FAULT. Shutdown uses the same
three immediate attempts and sparse 60-second cleanup as M6A; cleanup success does
not restore capability health until reboot. Repeated stop requests cannot reset
the retry budget. A clean completed capture may be explicitly restarted.

## USB diagnostics

- `ACTIVITY START`: requests exactly one capture, without changing role/config.
  Replies `ACTIVITY CAPTURING samples=0`, or explicitly rejects PENDING, ABSENT,
  FAULT or BUSY. A rejected start does not reset a capture/result.
- `ACTIVITY?`: reads only current/latched state; no sensor operation. Reports IDLE,
  CAPTURING with sample count, STOPPING, READY, INVALID, or UNAVAILABLE with
  accel=PENDING/ABSENT/FAULT. Completion is queried, not automatically printed.
- READY/INVALID include samples, duration_ms, discontinuities, usability,
  mean_x/y/z_mg, axis_variance_sum_mg2, mean_magnitude_squared_mg2 and
  mean_abs_delta_mg. No behavior labels are produced.
- Results remain latched until another accepted START or reboot. `ACCEL?` retains
  its existing diagnostic/query-only behavior; runtime samples do not replace
  the boot sample. Existing ROLE parsing, line endings, bounded input processing
  and overflow rejection remain intact.

## Compatibility and non-evidence

Hardware presence is not activity enablement. There is no automatic boot or
periodic capture, no RequestedConfig activity field and no legacy role migration.
Role, location source, GNSS power, capability, transport, device identity, profile
and user identity remain separate.

No changes to TLP v1 bytes/fixtures, RF configuration/forwarding, GNSS scheduling
or 3V3_S/WB_IO2 ownership, identity/sequence, HistoryStore/flash allocation, BLE or
durable configuration. Features are neither transmitted nor stored persistently.
TX_DONE remains unrelated to contact evidence.

This is not the production activity service, classification, proof of animal
behavior accuracy, or the final duty-cycle/FIFO/interrupt policy. The M6B3
operator evidence below supports only the focused bounded capture path. It does
not establish exact 10 Hz physical sampling, measured current consumption,
physical I2C fault injection/sparse cleanup recovery, continuous always-on service,
RESTING/GRAZING/WALKING classification, RF activity transmission, activity
persistence, geofence runtime or trusted LOST/contact. The classifier and M6D
remain NOT IMPLEMENTED; M6C runtime remains not integrated.

## Observed effective sampling interval

Both usable 50-sample windows reported `duration_ms=5790`: over 49 adjacent
intervals, the effective average is `5790 / 49 = 118.16 ms`, approximately
`49 * 1000 / 5790 = 8.46 Hz` (roughly 8.5 Hz). This is an average inferred from
the recorded window duration, not proof of uniform intervals or exact physical
10 Hz sampling.

This is not a timing-quality failure: `discontinuities=0` and `usable=yes` agree
with the current M6B contract allowing adjacent intervals of 50..300 ms and a
50-sample duration of 2450..14700 ms. The nominal 100 ms / 10 Hz / approximately
5-second values remain implementation seeds. Before classifier thresholds or
models are frozen, field data and feature sensitivity to effective sample-rate
variation must be considered. This documentation closure changes no timing policy.
