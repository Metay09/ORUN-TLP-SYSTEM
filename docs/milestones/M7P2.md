# M7P2 — Persistent layout constants + application flash ceiling build guard

Status: **HOST PASS; BUILD PASS; DELIBERATE NEGATIVE TEST CONFIRMED FIRING; NO
RUNTIME/PROTOCOL/HISTORY-FORMAT CHANGE.**

Baseline: `main@09d9820c803eaabe5b93f76b72b3964c2f98c7bd` (M7P1 ADR merged).
Branch: `feat/m7p2-storage-layout-guard`.

## Purpose

M7P1 (`docs/architecture/ADR_M7_PERSISTENCE_LAYOUT.md`) decided, but did not
implement, a future partition plan for BLE bonds, durable config, and
security material, carved from currently-unused application flash headroom,
strictly below the unchanged history journal. M7P2 implements only the
layout/build-guard slice of that ADR:

1. Adds the six decided addresses as inert `constexpr` layout constants with
   compile-time `static_assert` invariants.
2. Extends `firmware/scripts/check_storage_layout.py` with a post-link
   build guard that fails the build if the linked application ever occupies
   any byte at or above the new policy ceiling.

**Not done in M7P2** (all deferred to later ADR-numbered slices): BLE
enablement, SoftDevice runtime enablement, `InternalFS` relocation,
`FlashMutationGate`, any async flash backend, `ConfigStore`, `SecurityStore`,
bond storage, DFU, any `HistoryStore`/journal format change, and any TLP v1
change.

## Exact partition policy (unchanged from the ADR)

```text
0x026000 .. 0x0E7000   Application (reduced policy ceiling)
0x0E7000 .. 0x0E9000   Security material + anti-replay counters (2 pages, raw A/B)
0x0E9000 .. 0x0EB000   Durable config (2 pages, raw A/B)
0x0EB000 .. 0x0ED000   BLE bonds / relocated InternalFS (2 pages)
0x0ED000 .. 0x0F4000   Existing ORUN history journal (UNCHANGED, 7 pages, exclusive)
0x0F4000 .. 0x100000   Bootloader/settings (UNCHANGED)
```

## New constants (`firmware/include/storage_config.h`)

Added to the existing `orun_tlp::storage_config` namespace, directly below the
existing history constants — no new namespace, no history constant changed:

```text
kFutureSecurityRegionPages = 2
kFutureConfigRegionPages   = 2
kFutureBondRegionPages     = 2

kFutureSecurityRegionStart = 0x0E7000
kFutureSecurityRegionEnd   = kFutureSecurityRegionStart + 2 * kPageSize   (0x0E9000)
kFutureConfigRegionStart   = kFutureSecurityRegionEnd                    (0x0E9000)
kFutureConfigRegionEnd     = kFutureConfigRegionStart + 2 * kPageSize     (0x0EB000)
kFutureBondRegionStart     = kFutureConfigRegionEnd                      (0x0EB000)
kFutureBondRegionEnd       = kFutureBondRegionStart + 2 * kPageSize       (0x0ED000)

kApplicationPolicyEndAddress = kFutureSecurityRegionStart                (0x0E7000)
```

`kFutureBondRegionEnd` is derived from the page arithmetic above and is
statically asserted equal to the pre-existing `kBaseAddress` (history start,
`0x0ED000`) — it is not a second, independently-typed literal that could
silently drift from history's own address.

Twelve new `static_assert`s enforce, at compile time: page alignment of
every new boundary (4 asserts); each new region is exactly its declared page
count (3 asserts); the four regions (application-ceiling | security |
config | bond) are exactly contiguous with no gap and no overlap by chained
equality (4 asserts); and history's start (`kBaseAddress == 0x0ED000`) is
explicitly re-asserted unchanged by this layout (1 assert). All twelve pass,
alongside the two pre-existing history `static_assert`s (unmodified);
verified by compiling the header standalone
(`g++ -std=c++17 -Wall -Wextra -Werror`) and by the full `pio run` build
below.

These are **inert layout constants only** — nothing in the linked firmware
reads, writes, or otherwise references any `kFuture*` symbol; they exist
purely as the compile-time-checked single source of truth for the guard
described next and for later implementation slices.

## Soft ceiling guard (`firmware/scripts/check_storage_layout.py`)

A new post-link `env.AddPostAction` (`check_application_ceiling`), added
alongside the existing M4 `check_exclusive_owner` action, not replacing it:

- Reads `kApplicationPolicyEndAddress`'s value by parsing the *literal*-bearing
  symbol `kFutureSecurityRegionStart` directly out of `storage_config.h` at
  build time (`_application_policy_ceiling()`), so the ceiling has exactly
  one source of truth — the C++ header — rather than a second hardcoded
  literal in the Python script. (`kApplicationPolicyEndAddress` is itself
  defined equal to that symbol, with a `static_assert` enforcing the
  equality, so parsing either is equivalent.)
- Computes the highest actually-occupied flash byte from
  `arm-none-eabi-objdump -h` output (`_highest_flash_load_end()`), a small
  pure function taking only text and returning an integer, with no
  PlatformIO/`env` dependency — factored out for clarity, though this repo
  has no Python unit-test harness to exercise it against (see "Testability"
  below).
- Uses each section's **load address (LMA)**, not its virtual/run address
  (VMA), and only counts sections carrying the **`LOAD`** flag. This
  correctly includes `.text`/`.rodata`/`.ARM.exidx` and `.data`'s flash-resident
  initial-value image, and correctly **excludes** `.bss`/`.heap` (`ALLOC`
  only, no flash bytes consumed) even though the linker still prints a
  placeholder LMA for them. Verified directly: the helper's result on the
  real build (`0x49ec8`) matches the toolchain's own reported Flash-used
  figure exactly (`0x49ec8 - 0x26000 = 147,144` bytes).
- Fails the build with an actionable `RuntimeError` reporting the configured
  ceiling, the detected highest occupied address, and the exact excess in
  bytes when the ceiling is reached or exceeded.
- Is a **build-time policy guard, not a linker `MEMORY`-region change**. The
  audited, stock `nrf52840_s140_v6.ld` is untouched and still physically
  permits linking all the way to `0x0ED000`; patching the linker was
  deliberately deferred (see "Limitations" below).

## Why the linker is intentionally not patched yet

Patching the vendored linker script's `FLASH` `LENGTH` would give a true
hardware/linker-level reservation, but it is a **third vendor core patch**
(alongside the existing R4 Wire patch and R2.1 SX126x patch) for a
reservation that, as of M7P2, protects **zero implemented partitions** — no
`ConfigStore`, `SecurityStore`, or relocated `InternalFS` exists yet to be
protected. The ADR (§6) explicitly recommends starting with the soft
build-guard first and treating a hard linker patch as a later, optional
hardening step once the partitions it protects actually exist and are in
use. This keeps M7P2 a small, reviewable, build-tooling-only change.

## Deliberate negative/breakage test (required evidence)

A temporary, uncommitted payload was added to `firmware/src/main.cpp` (never
part of any commit on this branch):

```cpp
namespace { alignas(4) const uint8_t kOrunM7P2OversizeTest[650000] = {1,2,3,4,5}; }
// in setup(): read kOrunM7P2OversizeTest[millis() % 650000] and print it.
```

The read index is genuinely runtime-computed (`millis()`, not known at
compile time) specifically so the compiler cannot constant-fold the access
and eliminate the array — an earlier attempt using compile-time-constant
indices (`[0]` and `[649999]`) was silently optimized away by the compiler
(observed: Flash grew by only 48 bytes instead of ~650,000), which is itself
useful evidence that the ceiling check must measure the *actual linked
image*, not an assumed source size.

Build result with the oversized payload present:

```text
*** RuntimeError : M7P2 application flash ceiling exceeded: configured
ceiling is 0x0E7000, highest occupied flash byte end is 0x0E8A28 (exceeds
by 6696 bytes). This range is policy-reserved for the M7P1 security/config/
bond layout (docs/architecture/ADR_M7_PERSISTENCE_LAYOUT.md).
```

This is the new M7P2 guard firing specifically (not a generic linker
out-of-space error — the payload size was deliberately chosen to stay under
the *hard* linker capacity of 815,104 bytes while exceeding the new
*policy* ceiling of 790,528 bytes, so the failure mode observed is
unambiguously the M7P2 check, not `region 'FLASH' overflowed`).

The temporary payload was then fully removed (`git checkout --
firmware/src/main.cpp`); `git status`/`grep` confirmed no trace remained.
The normal build was re-run and passed again with identical RAM/Flash
figures to the pre-test baseline (147,144 / 815,104 bytes).

## Testability of the guard script

`_highest_flash_load_end()` is factored out as a small, pure function (no
`env`/PlatformIO dependency, input text in, integer out) specifically so it
*can* be unit-tested in principle. This repository's only existing test
harness (`firmware/tests/run_host_tests.sh`) compiles and runs C++ binaries;
there is no Python test framework anywhere in the repo, and introducing one
solely for this one helper would be exactly the "speculative tooling
architecture" this slice was told to avoid. No standalone
`python3 check_storage_layout.py` self-test entry point was added either:
doing so would require restructuring the file's existing unconditional
`Import("env")` call (present since the original M4 guard) into the
conditional `if "Import" in globals():` idiom `patch_wire.py`/`patch_radio.py`
already use, purely to support a test hook — a larger, riskier change to an
already-security-critical build guard than this slice's scope justifies. The
required deliberate oversized-build breakage test above is the validation
evidence for this guard, and is a stronger end-to-end proof (it exercises
the real toolchain, the real ELF, and the real error path) than a synthetic
unit test against recorded sample `objdump` text would have been.

## System impact review

- **Backward compatibility**: no packet bytes changed; no persistence bytes
  changed; no history migration; no mixed-fleet impact.
- **Power/RF**: no runtime impact — nothing in this change executes on the
  device; it is a compile-time constant addition and a build-time guard.
- **Storage**: history ownership unchanged; 24,576 bytes (6 pages) are now
  policy-reserved directly above history; no owner writes to any of the
  three new regions yet — no code references them at all.
- **BLE**: still disabled/not implemented.
- **DFU**: no bootloader behavior claim made or implied. The future maximum
  application image size *policy* ceiling is now 790,528 bytes (the *hard*
  linker/board maximum remains 815,104 bytes, unchanged). Dual-bank/rollback
  bootloader capability remains unresolved (decision gate F,
  `ORUN_STORAGE_FLASH_OWNERSHIP.md`).
- **Security**: addresses reserved only; no cryptography, no keys, no
  anti-replay logic implemented.

## Limitations

- This guard is a **build-time policy check**, not a hardware- or
  linker-level reservation. The stock, audited linker script still
  physically permits linking all the way to `0x0ED000`.
- Removing, bypassing, or disabling `check_storage_layout.py` (or this
  specific `AddPostAction`) would silently remove this protection — the
  stock linker would then accept an application that grows into the
  policy-reserved region without any error, exactly as it did before M7P2.
- No enforcement exists yet against a hand-edited `platformio.ini` that
  skips the `pre:`/post-link scripts entirely; this is the same
  pre-existing limitation the M4 guards already have, not a new one
  introduced here.
